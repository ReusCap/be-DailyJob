# be-DailyJob

### 1. 오늘 완료한 것

- 오늘 실제로 끝낸 기능/수정/학습:
  - 이슈 18의 구간표 값을 확정했다. 목표 비율을 현재가의 0.2~0.5%로 잡고 5구간으로 나눴다. 적용 방식은 현재가에 상승가를 더하는 게 아니라, 상승가의 배수 중 현재가보다 큰 최솟값을 쓰는 격자 방식으로 정했다.
  - 도커로 MySQL 8.4를 띄우고 스프링에서 붙는 것까지 확인했다. 엔티티로 테이블이 생기는 것도 SHOW TABLES로 직접 봤다.
  - application.yml에 spring.sql.init.mode를 always로, spring.jpa.defer-datasource-initialization을 true로 추가했다. 앞의 것이 없으면 MySQL에서는 data.sql이 아예 실행되지 않고, 뒤의 것이 없으면 테이블 생성 전에 INSERT가 돌아서 기동이 실패한다.
  - BidIncrementTier 엔티티를 만들고 data.sql로 구간 5행을 시드했다.
  - BidIncrementPolicy에 구간 선택과 격자 계산을 넣고 단위 테스트 14개를 작성했다. DB도 스프링도 없이 도는 순수 테스트다.
  - 구간 조회 실패 시 예외 타입을 BusinessException에서 IllegalStateException으로 바꾸고, 쓰이지 않게 된 BidErrorCode는 삭제했다.

- (오늘의 목표 중에서) 아직 끝내지 못한 부분:
  - presentation 계층. 구간표 조회 API와 컨트롤러 테스트가 남았다.
  - 기동 시 구간표 정합성 검증은 하려다가 뺐다. 못 한 게 아니라 안 하기로 판단한 것이라 4번에 적었다.

### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  구간표 테이블에 상한 컬럼을 두지 않고 하한만 저장했다. 상한은 다음 행의 하한으로 암묵적으로 정해지고, 마지막 구간은 상한이 없다.

- 그렇게 판단한 이유:
  상한을 같이 저장하면 (0, 500만) 다음에 (600만, 3000만)처럼 빈 구간이 생기거나, 범위가 겹치는 행이 데이터만으로 만들어진다. 하한만 두면 그런 상태가 애초에 표현 자체가 불가능하다. 이슈 체크리스트에 빈 구간이 있을 때 잘못된 금액으로 입찰이 처리되지 않아야 한다는 항목이 있었는데, 검증 코드로 막는 것보다 만들 수 없게 하는 쪽이 확실하다고 봤다. 마지막 구간의 무한대 상한을 특수값으로 처리할 필요가 없어지는 것도 이유였다.

- 고려했지만 선택하지 않은 대안:
  하한과 상한을 둘 다 저장하는 방식. 조회 쿼리가 BETWEEN으로 직관적이라는 장점이 있었다. 대신 겹침과 구멍을 코드로 계속 검사해야 하고, 마지막 구간 상한을 NULL이나 Long.MAX_VALUE 같은 값으로 둬야 해서 지저분해진다. 구간표를 코드 상수로 두는 방법도 있었지만, 구간 조정에 배포가 필요해지고 사용자가 기준을 조회할 수 없어서 제외했다.

- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  조회가 하한 이하인 구간 중 하한이 가장 큰 것을 고르는 방식으로 바뀌면서 정렬이 필요해졌다. findAll의 반환 순서를 신뢰할 수 없어서 BidIncrementPolicy 생성자에서 정렬하도록 했고, 입력 순서를 일부러 흐트러뜨린 테스트로 그 정렬이 실제로 도는지 확인했다.
  대신 빈 구간 관련 검증 로직이 통째로 사라졌다. 나중에 기동 시 검증을 안 넣기로 판단한 것도 여기서 이어진다. 구조로 막은 것을 코드로 또 막을 이유가 없었다.

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  docker compose up -d로 컨테이너를 띄운 직후 mysql 클라이언트로 붙었는데 ERROR 2002가 났다. /var/run/mysqld/mysqld.sock 소켓으로 접속할 수 없다는 내용이었다.

- 처음 추측한 원인:
  compose 파일 설정이 잘못됐거나 계정이 안 만들어진 줄 알았다.

- 원인을 확인하기 위해 시도한 방법:
  docker compose ps로 컨테이너 상태를 봤더니 Up이었다. 컨테이너는 살아있는데 왜 안 되는지 이해가 안 돼서 docker compose logs로 로그를 봤다.

- 실제 원인:
  볼륨이 방금 새로 만들어져서 MySQL이 데이터 디렉토리를 초기화하는 중이었다. 시스템 테이블 생성, DB 생성, 계정 생성이 끝나기 전이라 mysqld가 아직 안 떠 있었고, 그래서 소켓 파일 자체가 존재하지 않았다. 컨테이너가 Up인 것과 DB가 접속을 받을 준비가 된 것은 다른 얘기였다.

- 해결 방법:
  로그에 MySQL init process done과 ready for connections가 뜰 때까지 기다린 다음 다시 붙으니 됐다. 이후로는 로그를 읽는 것보다 mysqladmin ping으로 확인하는 게 빨랐다.

- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  컨테이너 상태와 그 안에서 도는 프로세스의 준비 상태를 구분해서 본다. 그리고 첫 부팅 로그에는 ready for connections가 두 번 나오는데, 초기화용 임시 서버 것과 진짜 서버 것이라 MySQL init process done 뒤에 오는 걸 봐야 한다는 것도 알았다.
  compose에 healthcheck를 넣으면 docker compose ps에서 healthy로 바로 보인다는 것도 확인했다. 다만 공용 파일이라 팀에 먼저 제안하기로 했다.

### 4. 오늘 잘한 행동(개발과 관련된 것)

- 어떤 행동이었는지:
  이해가 안 되는 예제 코드에 대해 이게 왜 필요한지 계속 따져봤다. 그리고 단계마다 실제로 눈으로 확인하고 넘어갔다. 엔티티 만들고 SHOW TABLES, data.sql 넣고 SELECT 하는 식이다.

- 그 접근이 도움이 된 이유:
  기동 시 구간표 정합성 검증을 넣으려다가 뺐다. 지금 구간표가 바뀌는 경로는 data.sql 하나뿐이고 PR 리뷰를 거치는데, 그 상황에서 런타임 검증이 뭘 막는지 설명이 안 됐다. 게다가 이슈의 구간 경계 검증 항목은 이미 작성한 경계값 테스트 5개가 커버하고 있었다. 중복이었다.
  예외 타입도 같은 방식으로 바뀌었다. 처음에는 팀 컨벤션이 ErrorCode와 BusinessException이니까 그대로 따랐는데, BusinessException은 사용자가 규칙을 어겼을 때 쓰는 것이고 구간표가 깨진 건 서버 데이터 문제라 범주가 맞지 않았다. IllegalStateException으로 바꾸니 로그에 스택 트레이스가 남고, 예외 메시지가 응답에 노출되지 않아서 현재가와 구간 행 수 같은 진단 정보를 담을 수 있게 됐다.
  확인하면서 진행한 것도 도움이 됐다. 문제가 생겼을 때 방금 바꾼 게 하나뿐이라 범인을 찾을 필요가 없었다.

- 다음에도 반복하고 싶은 점:
  리뷰어가 물어볼 것을 내가 먼저 묻는다. 설명하지 못하는 코드는 넣지 않는다. 넣지 않기로 한 것도 이유를 적어두면 그 자체가 판단 기록이 된다.

### 5. 오늘 아쉬웠던 행동(개발과 관련된 것)

- 비효율적이었던 접근/놓치거나 부족했던 점:
  원래 계획은 presentation 계층까지 끝내고 PR까지 올리는 것이었는데 도메인과 계산 로직에서 멈췄다. 이슈 하나를 하루에 마무리한다고 잡았던 견적이 실제와 맞지 않았다.

- 그렇게 된 원인:
  스프링과 JPA, 도커가 전부 처음이라 코드를 쓰는 시간보다 확인하는 시간이 길었다. 엔티티 어노테이션이 실제로 어떤 테이블을 만드는지, 리포지토리 인터페이스에 본문이 없는데 왜 findAll이 동작하는지, 빈으로 등록되는 것과 그냥 객체로 만드는 것의 기준이 뭔지 같은 걸 그때그때 짚고 넘어갔다. 이 시간 자체는 필요했다고 보지만, 일정을 잡을 때 그걸 계산에 넣지 않은 게 문제였다. 익숙한 작업처럼 견적을 냈다.

- 다음에는 다르게 해볼 구체적인 행동:
  처음 다루는 기술이 들어간 이슈는 구현 시간과 학습 시간을 따로 잡아서 견적을 낸다. 오늘 기준으로는 절반 이상이 학습이었다.
  이슈가 여러 계층에 걸치면 PR도 계층 단위로 쪼갠다. 도메인과 계산 로직까지 한 PR, presentation 계층을 다음 PR로 나눴으면 오늘 안에 리뷰를 시작할 수 있었다. 커밋은 이미 작업 단위로 끊어놨으니 PR을 나누는 것도 어렵지 않았을 거다.
  내일은 남은 presentation 계층을 먼저 끝내고 PR부터 올린 다음, 리뷰를 기다리는 동안 다음 이슈를 본다.
