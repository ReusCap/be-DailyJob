### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - data.sql과 application.yml의 spring.sql.init 설정을 지우고, 구간표 시드를 테스트 픽스처로 옮겼다

- 그렇게 판단한 이유:
  - application.yml이 하나뿐이라 로컬 편의를 위한 설정이 운영에도 그대로 적용되는 구조였다
  - 테스트가 통과하려고 필요한 데이터를 운영 설정이 떠안고 있었다, 책임 위치가 틀렸다고 봤다
  - 테스트가 자기 데이터를 스스로 준비하면 무엇에 의존하는지 파일 하나로 드러난다

- 고려했지만 선택하지 않은 대안:
  - 프로파일을 분리해서 application-local.yml에만 남기기, 지금 프로파일 체계 자체가 없어서 이 이슈에 넣기엔 범위가 컸다
  - Flyway 마이그레이션으로 옮기기, 엔티티가 방금 만들어진 참이라 마이그레이션 파일만 쌓일 것 같아 이르다고 봤다

- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  - 테스트가 @Sql로 픽스처를 명시하니 어떤 데이터로 도는지 코드에서 바로 보인다
  - 운영 설정에서 개발 편의 설정이 빠져서 application.yml을 고칠 때 부담이 줄었다
  - 대신 로컬 DB에 구간표가 없어서 앱을 띄워도 조회 API가 빈 목록을 준다, 이건 아직 열려 있는 문제다

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - 시드를 @Sql 픽스처로 옮긴 뒤 조회 API 테스트에서 구간 개수가 5개가 아니라 10개로 나왔다

- 처음 추측한 원인:
  - 픽스처 파일이 두 번 로드되거나 경로 설정이 잘못된 줄 알았다

- 원인을 확인하기 위해 시도한 방법:
  - 클래스 레벨 @Sql이 언제 실행되는지 확인했다
  - 테스트 메서드가 두 개인 것과 행이 정확히 두 배인 게 맞물려서 메서드마다 도는지 의심했다

- 실제 원인:
  - 클래스 레벨 @Sql은 테스트 메서드마다 실행되는데, @SpringBootTest는 @Transactional이 없으면 롤백을 하지 않는다
  - 그래서 앞 메서드가 넣은 5행이 남은 상태에서 다음 메서드가 5행을 더 넣었다

- 해결 방법:
  - 픽스처 첫 줄에 delete from bid_increment_band를 넣어서 매 테스트가 같은 상태에서 시작하게 했다

- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - 통합 테스트에서 데이터를 넣을 때 롤백이 되는 구조인지부터 본다
  - 테스트가 앞 테스트의 상태에 의존하지 않는지 확인한다, 메서드를 하나 추가했을 때 깨지면 그게 신호다
  - 팀에서 논의 중인 Testcontainers가 정확히 이 문제를 푸는 도구라는 걸 알게 됐다

### 4. 오늘 잘한 행동(개발과 관련된 것)

- 어떤 행동이었는지:
  - 리팩터링을 한 커밋에 몰지 않고 관심사별로 다섯 개로 쪼갰다
  - 팀원 코드와 다른 지점을 취향 문제로 넘기지 않고 컨벤션 항목으로 정리해서 확인한 다음 맞췄다
  - 리포지토리 위치도 그냥 옮긴 게 아니라 왜 domain에 두는지 확인하고 옮겼다

- 그 접근이 도움이 된 이유:
  - 명명 통일처럼 파일을 여러 개 건드리는 변경이 다른 변경을 가리지 않는다, 커밋 하나에 몰았으면 리뷰어가 뭘 봐야 할지 못 찾았을 거다
  - ResponseEntity와 @RequiredArgsConstructor는 팀원 코드와 기존 코드가 서로 달랐는데, 어느 쪽으로 갈지 정하고 나서 고쳤다
  - 내 코드만 조용히 맞추는 것보다 팀 규칙으로 만드는 쪽이 다음 사람에게도 남는다

- 다음에도 반복하고 싶은 점:
  - 리팩터링 커밋에는 한 종류만 담는다
  - 다른 사람 코드와 다른 지점을 발견하면 내 것만 고치기 전에 규칙으로 만들 수 있는지 본다

  - 확정했다고 본 산출 방식을 구현과 테스트까지 다 만든 뒤에 정정했다

- 그렇게 된 원인:
  - 코드를 쓰기 전에 팀 컨벤션을 확인하지 않았다, 컨트롤러 반환 타입이나 주입 방식은 이미 팀원 코드에 답이 있었는데 열어보지 않고 시작했다
  - 리포지토리도 무심코 infrastructure에 뒀다, 어디가 맞는지 따져본 게 아니라 폴더가 있어서 넣은 것에 가까웠다
  - 산출 방식은 이슈 단계에서 확정으로 판단했는데, 그 판단에 검토가 덜 들어갔다

- 다음에는 다르게 해볼 구체적인 행동:
  - 새 계층이나 새 클래스를 만들기 전에 같은 자리의 팀원 코드를 먼저 열어본다, 반환 타입과 주입 방식 정도는 5분이면 확인된다
  - 규칙을 확정할 때 대표 케이스 두세 개를 손으로 계산해서 이슈에 같이 적는다, 표만 적고 넘어가면 나중에 뒤집게 된다
  - 컨벤션이 갈리는 지점을 발견하면 그때 팀에 올린다, 오늘 것도 코드를 다 쓴 뒤에 발견해서 리팩터링이 됐다
