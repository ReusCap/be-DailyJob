# be-DailyJob

### 1. 오늘 완료한 것

- 오늘 실제로 끝낸 기능/수정/학습:
  - Public Subnet과 Private Subnet의 차이를 외부 통신 가능 여부와 트래픽 흐름을 기준으로 정리했다
  - WAS, MySQL, NAT, Nginx/ALB, Redis가 각각 어떤 책임을 가지는지 식당 구조에 빗대어 이해했다
  - 현재 팀 제약인 WAS EC2 1대, DB EC2 1대, NAT 인스턴스 1대에 맞는 기본 배포 구조를 정리했다
  - 서버 대수 제한이 풀렸을 때 Nginx/ALB, RDS, Redis를 어떤 목적과 순서로 도입할지 확장 구조를 비교했다
  - 앞으로 남은 2주 동안 진행할 스프린트 범위를 팀과 확정했다

- 아직 끝내지 못한 부분:
  - 정리한 구조를 실제 AWS 환경에 구성하고 요청 흐름을 검증하는 작업은 남아 있다
  - 보안 그룹과 라우팅 테이블에서 각 서버 사이에 어떤 포트와 경로만 허용할지 구체화하지 못했다
  - 스프린트 범위는 확정했지만 일정 안에서 발생할 수 있는 배포 문제와 기술 부채의 우선순위까지 세분화하지는 못했다

### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - 현재 팀의 서버 대수 제한에서는 WAS를 Public Subnet에 두고, MySQL만 Private Subnet에 숨기는 구조로 시작한다

- 그렇게 판단한 이유:
  - 외부 요청을 처음 받을 ALB나 Nginx 서버가 따로 없어서 사용자가 접근하려면 WAS가 직접 진입점이 되어야 한다
  - 반대로 MySQL은 사용자의 직접 접근을 받을 이유가 없고 WAS와만 통신하면 되므로 Private에 두는 게 맞다
  - Private의 DB가 패키지 설치나 업데이트를 위해 인터넷으로 나갈 때는 Public의 NAT 인스턴스를 통하게 하면 외부에서 DB로 들어오는 경로를 열지 않아도 된다
  - 지금 가진 자원 안에서 서비스 접근성과 DB 보안을 동시에 만족시키는 구조라고 판단했다

- 고려했지만 선택하지 않은 대안:
  - WAS를 처음부터 Private에 두는 구조를 생각했지만, 그러려면 외부 요청을 대신 받을 ALB나 Nginx가 추가로 필요해 현재 서버 제한과 맞지 않는다
  - RDS와 Managed NAT Gateway를 쓰는 방식은 운영 부담을 줄일 수 있지만, 이번 단계의 직접 구축 조건과 비용을 고려해 선택하지 않았다
  - Redis도 검토했지만 현재는 캐시로 해결해야 할 트래픽 문제가 확인되지 않았고, WAS를 Private으로 옮기기 위한 구성 요소도 아니어서 뒤 단계로 미뤘다

- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  - 애플리케이션 코드보다 먼저 배포 환경에서 누가 외부 요청을 받고 누가 누구에게만 접근할 수 있는지 경계가 분명해졌다
  - 현재 구조를 임시방편으로만 보지 않고, 제약 안에서 선택한 1단계 구조로 설명할 수 있게 됐다
  - 이후 Nginx/ALB를 도입하면 WAS를 Private으로 옮기고, 운영 부담이 커지면 EC2의 MySQL을 RDS로 교체한다는 확장 순서가 생겼다

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - WAS를 Private Subnet에 두게 만드는 요소가 Redis인지 Nginx인지 헷갈렸고, NAT가 있는데도 왜 Private 서버가 외부 요청을 직접 받을 수 없는지 연결되지 않았다

- 처음 추측한 원인:
  - Redis처럼 WAS와 가까이 붙는 서버가 추가되면 WAS도 함께 Private으로 이동하는 것이라고 생각했다
  - NAT를 Private 서버와 인터넷을 양방향으로 이어주는 통로처럼 이해했다

- 원인을 확인하기 위해 시도한 방법:
  - 각 구성 요소를 요청의 최초 진입점, 내부 처리, 데이터 저장, 외부로 나가는 통신으로 나눠서 다시 배치했다
  - 사용자 요청이 들어오는 흐름과 Private 서버가 업데이트를 받으러 나가는 흐름을 따로 그려봤다
  - 기본형, 실무 표준형, 고성능 확장형을 나란히 비교해서 어느 구성 요소가 추가될 때 서버 위치가 달라지는지 확인했다

- 실제 원인:
  - 서버 위치를 역할 이름으로 외우고 있었고 인바운드와 아웃바운드 통신 방향을 구분하지 못했다
  - Redis는 조회 속도를 높이는 캐시일 뿐 외부 요청을 대신 받지 않는다
  - WAS를 Private으로 옮길 수 있게 만드는 것은 Public에서 최초 요청을 받아 전달하는 Nginx나 ALB다
  - NAT는 Private 서버가 인터넷으로 나가는 경로를 제공할 뿐 인터넷에서 Private 서버로 들어오는 진입점이 아니다

- 해결 방법:
  - 사용자 → Public WAS → Private MySQL을 현재 구조로 정리했다
  - 확장 구조는 사용자 → Public ALB/Nginx → Private WAS → Private RDS로 정리했다
  - Redis는 Private에서 WAS와 RDS 사이의 조회를 보조하며, 캐시에 값이 없을 때만 RDS를 조회하는 선택적 구성으로 분리했다

- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - 구성 요소 이름부터 외우지 않고 외부 요청을 누가 처음 받는지부터 찾는다
  - 인바운드 요청과 아웃바운드 인터넷 접근을 별개의 흐름으로 그린다
  - 보안, 비용, 트래픽, 운영 편의 중 어떤 문제를 해결하려고 추가한 구성인지 확인한다

### 4. 오늘 잘한 행동

- 어떤 행동이었는지:
  - AWS 서비스를 한 번에 많이 붙이는 대신 현재 제약에서 가능한 구조와 이후 확장 구조를 3단계로 나눴다
  - Public/Private, NAT, ALB, Redis처럼 헷갈리던 개념을 식당의 홀, 주방, 심부름꾼, 안내데스크, 도마에 대응시켜 역할을 구분했다
  - 남은 2주 스프린트 범위를 확정해 학습한 인프라 개념을 실제 프로젝트 일정과 연결했다

- 그 접근이 도움이 된 이유:
  - 현재 구조에 ALB, RDS, Redis가 없다는 이유만으로 부족한 설계라고 보지 않게 됐다
  - 각 서비스가 해결하는 문제가 다르다는 걸 알게 되어 Redis를 넣으면 WAS가 Private으로 이동한다는 식의 잘못된 연결을 끊을 수 있었다
  - 최종 구조를 한 번에 만들려 하기보다 현재 조건에서 동작하는 구조를 만들고 필요가 생길 때 확장한다는 기준이 생겼다

- 다음에도 반복하고 싶은 점:
  - 새로운 기술을 공부할 때 정의만 적지 않고 현재 프로젝트에서 어디에 놓이며 왜 필요한지까지 연결한다
  - 아키텍처를 고를 때 가장 좋아 보이는 구성이 아니라 현재의 자원 제한과 해결할 문제부터 확인한다
  - 스프린트 시작 전에 범위를 확정하고 학습 과제가 실제 구현의 어떤 판단에 쓰이는지 남긴다

### 5. 오늘 아쉬웠던 행동

- 비효율적이었던 접근/놓치거나 부족했던 점:
  - 처음에는 Public과 Private을 서버 종류에 따라 정해지는 고정 위치처럼 받아들였다
  - NAT, Nginx/ALB, Redis를 모두 서버 사이의 중간 구성 요소로 묶어서 각각의 통신 방향과 목적을 구분하지 못했다
  - 아키텍처 단계는 정리했지만 장애 대응, 가용 영역 분리, 백업, 모니터링 같은 운영 관점까지는 살펴보지 못했다

- 그렇게 된 원인:
  - 개별 서비스의 정의를 먼저 외우고 실제 요청이 이동하는 경로를 그리지 않았다
  - 실무 표준형이 항상 더 좋은 정답이라고 생각해서 현재 팀의 비용과 서버 수 제한을 설계 조건으로 충분히 보지 않았다
  - 남은 스프린트 범위를 정하는 데 집중해 배포 이후의 운영 시나리오까지 논의를 확장하지 못했다

- 다음에는 다르게 해볼 구체적인 행동:
  - AWS 구성 전에 사용자 요청, 내부 DB 접근, 외부 업데이트 경로를 각각 화살표로 그린다
  - 구성 요소를 추가할 때 해결하려는 문제와 추가 비용을 한 줄씩 같이 적는다
  - 실제 구축에서는 보안 그룹 규칙과 라우팅 테이블을 문서화하고, Public에서 DB로 직접 접근할 수 없는지 검증한다
  - 2주 스프린트 중간에 범위와 진행 상황을 다시 확인해 배포 검증이나 운영 준비가 마지막에 밀리지 않게 한다
