# be-DailyJob

### 1. 오늘 완료한 것

- 오늘 실제로 끝낸 기능/수정/학습:
  - 데모 데이에 필요한 화면이 동작하도록 아침에 프론트엔드와 백엔드 API를 빠르게 연결했다
  - 데모 흐름을 기준으로 실제 요청과 응답이 이어지는지 확인하고 시연 준비를 마쳤다
  - 남은 2주 스프린트를 시작하면서 알림 기능에 사용할 실시간 통신 방식을 공부했다
  - 단순 폴링, 적응형 폴링, 롱 폴링, SSE, WebSocket, Web Push의 연결 방식과 비용을 비교했다
  - 현재 프로젝트의 알림 통신에는 WebSocket보다 SSE가 적합하다고 결론 내렸다
  - HTTP/1.1의 도메인당 커넥션 제한과 ALB/CloudFront에서 HTTPS 및 HTTP/2를 적용하는 구조까지 확인했다

- 아직 끝내지 못한 부분:
  - 아침에 급하게 연결한 프론트 API 코드를 데모 이후 다시 정리하고 예외 상황까지 검증해야 한다
  - 알림용 SSE 엔드포인트와 구독 채널은 아직 구현하지 않았다
  - SSE 재연결 사이의 이벤트 유실을 막을 `id`와 `Last-Event-ID` 처리 방식을 정하지 못했다
  - 페이지가 열린 채 SSE만 유지될 때 세션이 만료되는 문제의 해결 방법이 남아 있다

### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - 알림은 SSE로 내려주고, 읽음 처리처럼 클라이언트에서 서버로 보내는 동작은 기존 REST API로 분리한다

- 그렇게 판단한 이유:
  - 알림은 서버에서 클라이언트로만 전달되는 저빈도 이벤트라 WebSocket의 양방향 통신과 작은 프레임이 주는 이점이 크지 않다
  - 폴링은 구현이 단순하지만 이벤트가 없어도 요청과 DB 조회가 반복되어 1vCPU 서버에서 대부분 빈 응답을 처리하게 된다
  - SSE는 HTTP 위에서 동작하고 브라우저의 `EventSource`가 자동 재연결과 `Last-Event-ID`를 지원한다
  - 현재 인증 방식이 세션 쿠키라 `EventSource`에서 `Authorization` 커스텀 헤더를 넣지 못하는 제약에도 걸리지 않는다
  - 기존 경매방의 `RoomChannel`, `RoomSubscriber`, `SseRoomSubscriber` 구조를 사용자 ID 기준 알림 채널로 확장할 수 있어 새 의존성이 필요 없다

- 고려했지만 선택하지 않은 대안:
  - 단순 폴링은 데모 수준에서 가장 빨리 만들 수 있지만 즉시성이 폴링 주기에 묶이고 이벤트가 없어도 계속 요청한다는 비용 때문에 기각했다
  - 롱 폴링은 거의 실시간이지만 이벤트나 타임아웃마다 연결을 다시 맺어야 하고, SSE가 가능한 환경에서 선택할 이유가 적었다
  - WebSocket은 채팅처럼 양방향 고빈도 입력이 생기면 적합하지만 지금은 재연결, 인증, CSWSH 방어, 프록시 Upgrade 설정 비용만 늘어난다
  - Web Push는 브라우저가 닫혀 있어도 알림을 보낼 수 있지만 HTTPS, 서비스 워커, VAPID 키, 사용자 권한 동의가 필요하고 현재 요구 범위를 넘는다

- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  - 입찰과 읽음 처리는 REST, 서버 알림은 SSE라는 통신 방향이 분명해졌다
  - 이미 검증한 경매방 포트와 어댑터 패턴을 재사용할 수 있어 구현 범위와 학습 비용이 줄었다
  - 대신 이벤트 ID, 하트비트, 구독 해제, 세션 갱신처럼 장시간 연결에서 책임져야 할 항목이 명확해졌다
  - 인스턴스가 여러 대로 늘어나면 Redis Pub/Sub 같은 백플레인이 필요하다는 확장 시점도 정해졌다

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - 실시간 통신이면 WebSocket을 써야 한다고 생각했지만, 현재 알림 기능에 필요한 수준과 구현 비용이 맞는지 설명하기 어려웠다

- 처음 추측한 원인:
  - SSE와 WebSocket을 단순히 단방향과 양방향으로만 구분했고 연결 유지, 재연결, 인증, 서버 자원 사용까지 비교하지 않았다
  - SSE 연결 하나가 톰캣 스레드 하나를 계속 점유할 것이라고 생각했다

- 원인을 확인하기 위해 시도한 방법:
  - 통신 방식을 누가 연결을 여는지, 연결을 얼마나 유지하는지, 데이터가 어느 방향으로 흐르는지로 나눠 비교했다
  - 현재 서버 사양, 세션 인증, Nginx가 없는 HTTP/1.1 환경, 기존 SSE 코드라는 프로젝트 조건에 각각 대입했다
  - 단순 폴링을 100명이 2초 간격으로 수행하는 경우 초당 50개의 요청이 생긴다는 식으로 비용을 계산했다
  - 기존 `SseRoomSubscriber`와 구독 정리 코드를 기준으로 실제 재사용 범위와 빠진 기능을 확인했다

- 실제 원인:
  - 기술의 일반적인 장단점만 보고 우리 프로젝트의 이벤트 방향과 빈도, 인증 방식, 서버 수를 판단 기준에 넣지 않은 것이 문제였다
  - `SseEmitter`는 서블릿 비동기 기반이라 연결마다 톰캣 워커 스레드를 하나씩 계속 붙잡는 구조가 아니었다
  - 현재 병목 후보는 연결 개수보다 요청 스레드에서 구독자 수만큼 동기 전송하는 브로드캐스트 루프에 가까웠다

- 해결 방법:
  - 저빈도 단방향 알림에는 SSE, 클라이언트 입력에는 REST를 사용하는 것으로 역할을 분리했다
  - 채팅이나 커서 공유처럼 고빈도 양방향 입력이 생길 때만 WebSocket으로 판단을 뒤집기로 했다
  - 서버가 2대 이상이 되면 SSE를 버리는 대신 인스턴스 사이에 Redis Pub/Sub 백플레인을 추가하기로 했다
  - SSE 채널이 3개째 필요해지면 채널을 더 열지 않고 이벤트 타입을 다중화해 하나의 연결로 합치기로 했다

- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - 실시간이라는 이유만으로 WebSocket부터 고르지 않고 데이터 방향과 발생 빈도를 먼저 본다
  - 현재 인증 방식과 프록시, HTTP 버전, 서버 사양을 선택 조건에 포함한다
  - 새 기술이 주는 이점뿐 아니라 재연결, 유실 복구, 보안, 운영 설정까지 내가 구현해야 하는 비용을 적는다

### 4. 오늘 잘한 행동

- 어떤 행동이었는지:
  - 데모에 필요한 API 연결을 우선해서 제한된 시간 안에 시연 가능한 흐름을 만들었다
  - 폴링부터 Web Push까지 후보를 넓게 본 뒤 현재 프로젝트의 구체적인 제약을 기준으로 하나씩 기각했다
  - SSE 선택으로 끝내지 않고 커넥션 제한, 세션 만료, 단일 인스턴스 전제와 같이 선택 후 감수할 문제까지 적었다

- 그 접근이 도움이 된 이유:
  - 데모 직전에 완성도를 넓게 끌어올리려 하지 않고 실제로 보여줘야 할 사용자 흐름에 집중할 수 있었다
  - WebSocket이 더 실시간답다는 인상 대신, 현재 기능에는 SSE가 더 적은 비용으로 요구사항을 만족한다는 근거가 생겼다
  - `Last-Event-ID`, 하트비트, 구독 해제처럼 구현 전에 공부해야 할 지점이 코드 위치와 함께 드러났다

- 다음에도 반복하고 싶은 점:
  - 마감이 가까우면 데모의 핵심 경로를 먼저 연결하고 부가적인 정리는 별도 작업으로 남긴다
  - 기술 선택은 프로젝트의 실제 트래픽과 제약을 수치와 코드로 확인한 뒤 결정한다
  - 결론과 함께 그 결론을 뒤집을 조건도 기록한다

### 5. 오늘 아쉬웠던 행동

- 비효율적이었던 접근/놓치거나 부족했던 점:
  - 데모 당일 아침에 프론트 API를 바이브 코딩으로 급하게 연결했다
  - 화면이 동작하는 데 집중해서 응답 타입, 실패 응답, 로딩 상태, 중복 요청 같은 경계 조건을 충분히 확인하지 못했다
  - 실시간 통신 후보를 넓게 조사하면서 현재 스프린트에서 사용하지 않을 레거시 방식과 WebTransport까지 학습 범위가 커졌다

- 그렇게 된 원인:
  - 데모 전에 프론트와 백엔드의 실제 연결을 완료해야 하는 시점을 앞당겨 잡지 않았다
  - 성공 경로가 보이는 것을 연결 완료로 판단했고, API 계약과 예외 처리 확인을 위한 체크리스트가 없었다
  - 실시간 통신의 전체 지도를 먼저 보려다 당장 구현에 필요한 SSE의 세부 동작보다 후보 기술 비교에 시간을 많이 썼다

- 다음에는 다르게 해볼 구체적인 행동:
  - 데모 전날까지 API 연결을 끝내고 당일에는 데이터 초기화와 핵심 시나리오 리허설만 한다
  - 프론트 API를 연결할 때 성공, 빈 값, 인증 실패, 서버 오류의 네 가지 경우를 최소 확인 항목으로 둔다
  - 급하게 만든 코드는 데모 이후 정리할 항목을 바로 이슈로 남겨 임시 구현이 굳어지지 않게 한다
  - 다음 학습에서는 `Last-Event-ID`, `SseEmitter` 타임아웃, 콜백 기반 구독 해제, 하트비트, 세션 갱신처럼 실제 구현에 필요한 항목부터 검증한다
