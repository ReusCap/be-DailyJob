### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - 알림을 현재 상태를 설명하는 UI 문구가 아니라 **사건이 발생했을 때의 기록**으로 다루기로 함
  - 차량명·금액·상대 이름·일정은 발행 시점에 완성해 저장하고, 이동 링크는 조회 시점에 `type + referenceId`로 조립
  - 알림 행은 입찰·경매 종료·거래 확정과 같은 업무 트랜잭션에 함께 저장하고, SSE 전송만 커밋 뒤로 분리
- 그렇게 판단한 이유:
  - 조회 시점에 문구를 만들면 차량명이나 거래 일정이 바뀔 때 과거 알림의 내용까지 바뀜
  - 관련 경매나 거래가 삭제되면 과거 알림 문구를 조립하지 못할 수도 있음
  - 알림마다 관련 엔티티를 다시 조회하면 알림 목록 조회가 여러 도메인의 조회와 생명주기에 의존하게 됨
  - 반대로 링크는 프론트 라우트 변경을 따라갈 필요가 있어 완성된 문자열로 저장하면 과거 알림의 목적지가 낡음
  - 업무가 롤백됐는데 알림만 남거나, 커밋되지 않은 알림이 SSE로 먼저 보이는 상황은 막아야 했음
- 고려했지만 선택하지 않은 대안:
  - 조회할 때 경매·차량·거래를 다시 읽어 문구 조립
    - 최신 값은 반영되지만 과거 사건의 내용이 바뀌고 조회 책임이 여러 도메인으로 퍼짐
  - 차량명·금액·일정을 개별 컬럼이나 자유로운 payload로 저장
    - 알림 종류마다 nullable 컬럼이나 payload 버전 관리가 늘어 현재 규모에서는 과함
  - 업무 커밋 뒤에 알림 행까지 저장
    - 업무는 성공했지만 알림 저장이 실패해 영구 알림 자체가 사라질 수 있음
  - 트랜잭션 안에서 SSE까지 전송
    - 이미 브라우저에 보낸 데이터는 롤백할 수 없고 느린 연결이 DB 커넥션과 경매 잠금을 붙잡게 됨
- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  - 조회 API와 프론트는 저장된 `message`를 그대로 표시하므로 동적 문구가 늘어도 응답 계약이 바뀌지 않음
  - `NotificationContent` 팩터리가 알림 타입과 필요한 값을 묶어 잘못된 타입·문구 조합을 줄임
  - 기존 알림은 `defaultOf()` 경로를 유지해 이슈 범위 밖 호출부를 한꺼번에 바꾸지 않음
  - 문구는 사건 당시 값을 보존하면서 링크는 라우트 변경에 대응할 수 있게 됨
  - 입찰·종료·거래가 롤백되면 알림도 함께 롤백되고, SSE는 커밋된 알림만 전달됨

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - 상위 입찰 알림을 실제 브라우저 두 개로 확인하려 했는데 입찰 화면이 `호가 단위 불러오는 중`에서 진행되지 않음
  - DB에는 `bid_increment_band` 데이터가 있었지만 API는 빈 `bands`를 반환
  - 별도로 시드 스크립트에서 SQL 오류가 발생했는데도 성공 안내가 출력되는 문제도 있었음
- 처음 추측한 원인:
  - 데모 데이터가 부족하거나 프론트가 호가 구간 응답을 잘못 처리한다고 생각
  - 일부 테이블이 없어진 증상은 서버 재시작이나 시드 순서 문제라고 추측
- 원인을 확인하기 위해 시도한 방법:
  - 브라우저 Network에서 `/api/bid-increments` 응답 확인
  - MySQL에서 정책 테이블의 실제 행 확인
  - `BidIncrementService`의 캐시 생성 시점 확인
  - 8080 포트를 사용하는 프로세스와 백엔드 실행 로그 확인
  - 스키마 DDL 실행 시점과 포트 충돌 발생 순서를 대조
- 실제 원인:
  - 시드 스크립트가 서버 준비 확인을 위해 `/api/bid-increments`를 먼저 호출함
    - 이때 정책 테이블이 비어 있어 빈 `BidIncrementTable`이 메모리에 캐시됨
    - 이후 DB에 행을 넣어도 이미 만들어진 캐시가 계속 반환됨
  - 백엔드 두 개를 같은 DB에 `ddl-auto:create`로 실행함
    - 두 번째 서버는 포트 충돌로 최종 실행에는 실패했지만, 그 전에 일부 DDL을 수행해 스키마를 불완전하게 만듦
  - 스크립트에 `set -e`가 없어 SQL이 실패해도 성공 메시지가 계속 출력됨
- 해결 방법:
  - 서버 준비 확인을 업무 API가 아닌 `/actuator/health`로 변경
  - 정책 데이터를 넣은 뒤 처음으로 호가 구간 API를 호출하도록 순서 변경
  - 이미 빈 캐시가 만들어졌다면 백엔드를 재시작해 최초 적재부터 다시 수행
  - 백엔드는 하나만 실행하고, 로컬 데이터를 유지할 때는 `ddl-auto=none`을 명시
  - 새 검증 스크립트에 `set -euo pipefail`을 적용해 SQL 실패 시 즉시 종료
  - 두 계정으로 최고 입찰자를 번갈아 바꾸며 직전 최고 입찰자에게만 알림이 오는지 확인
- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - 준비 상태를 확인하려고 호출한 API가 캐시나 업무 상태를 바꾸는지
  - DB 값과 API 응답이 다르면 네트워크보다 애플리케이션 메모리 캐시를 먼저 확인
  - 서버가 포트 충돌로 실패했더라도 그전에 DDL이나 초기화 작업을 수행했는지
  - 스크립트의 성공 메시지가 실제 명령 성공을 보장하도록 실패 즉시 종료 옵션이 있는지

  - 이미 구현한 기능이라도 현재 사용자 가치가 없으면 유지 비용을 더 내지 않고 제거할 수 있었음

  - 프론트에서 즉시 띄우는 일반 토스트와 서버가 저장한 뒤 SSE로 전달하는 알림을 어떤 기준으로 나눌지 초기에 정하지 못함
  - 알림을 추가할 때마다 개별 사례로 판단해, 같은 사건을 화면·일반 토스트·서버 알림 중 어디에서 보여줘야 하는지 계속 다시 검토함
  - 특히 거래 확정처럼 행동한 사람에게는 요청 성공이고 상대방에게는 새로 확인해야 할 사건인 경우가 있어, 알림 종류만으로는 구분할 수 없었음
  - 실제 코드 변경량보다 기존 알림 발행 지점과 화면 토스트를 전수 확인하고 예외를 정리하는 데 훨씬 많은 시간이 들었음
- 그렇게 된 원인:
  - “실시간으로 보여줄 것인가”부터 생각했고, 사용자가 화면을 닫은 뒤에도 다시 확인할 가치가 있는지를 먼저 판단하지 않음
  - 서버 알림과 일반 토스트를 전달 기술의 차이로 봤지, 정보의 수명과 수신자의 행동 관점으로 구분하지 못함
  - 기준 없이 알림 종류별로 판단하면서 비슷한 사례가 나올 때마다 앞선 결론을 다시 검토함
- 고민 끝에 확정한 기준:
  - **화면을 닫았다가 다시 접속해도 확인할 가치가 있으면 알림 벨**
    - 서버에 저장하고 SSE로 즉시 전달
    - 실시간 팝업을 놓쳐도 알림 목록에서 다시 확인 가능
  - **현재 요청의 성공만 확인하면 끝나면 일반 토스트**
    - 사용자가 방금 수행한 요청의 결과만 짧게 확인
    - 별도 기록이나 재확인이 필요하지 않으므로 알림 벨에는 저장하지 않음
  - **현재 화면에 이미 보이는 변화라면 화면 자체로 표시**
    - 상태·결과·완료 화면이 같은 사실을 충분히 보여주면 별도 토스트를 추가하지 않음
    - 서버 알림이 저장될 가치가 있더라도 현재 그 목적지 화면을 보고 있으면 팝업만 생략
- 확정한 알림 벨 대상:
  - 평가 최초 승인·반려
  - 최고가 상실
  - 경매 개장 구독 알림
  - 낙찰·미낙찰 종료
  - 판매 차량 낙찰·유찰
  - 상대방에게 거래 차례가 넘어온 사건
  - 상대방의 거래 확정·취소
- 제거하거나 수정하기로 한 알림 벨:
  - 회원가입 환영 알림
  - 경매글 등록 직후 자기 자신에게 보내는 알림
  - 평가 결과 수정 시 반복되는 승인 알림
  - 구매자가 직접 확정한 인도 일정에 대한 구매자 자신의 알림
  - 과거 호환용 `AUCTION_WON_RESULT`, `DEAL_STATUS_CHANGED`
- 유지하기로 한 일반 성공 토스트:
  - 로그인·회원가입
  - 입찰
  - 경매글 수정·삭제
  - 평가 결과 제출·수정·반려
  - 거래 단계 제출·확정·취소
- 제거하기로 한 일반 성공 토스트:
  - 별도 완료 화면이 있는 방문견적 신청
  - 별도 완료 화면이 있는 경매 등록
  - 같은 사용자에게 서버 알림까지 중복되는 거래 확정 토스트
- 다음에는 다르게 해볼 구체적인 행동:
  - 알림 구현 전에 `사건·행동한 사람·수신자·다시 확인할 가치·현재 화면 노출 여부·딥링크 목적지`를 먼저 작성
  - 위 세 가지 기준으로 알림 벨·일반 토스트·화면 표시를 먼저 분류한 뒤 코드를 수정
  - 동일 사건이 사용자 역할에 따라 달라지는 경우를 별도로 확인
    - 내가 거래를 확정함 — 요청 성공이므로 일반 토스트
    - 상대방이 거래를 확정함 — 다시 확인할 사건이므로 알림 벨
  - 새 서버 알림을 추가할 때 같은 화면에서 이미 성공 토스트나 상태 변경을 보여주는지 함께 검색
  - 코드량이 적어 보여도 알림 정책을 정하는 작업은 전수 확인 비용이 크므로, 구현 일정에 정책 정리 시간을 별도로 잡기
