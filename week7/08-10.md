### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - 거래 단계를 "한 단계에 움직일 수 있는 사람이 정확히 한 명"인 순차 흐름으로 재구성
  - 그 결과로 진행 경로에 비관적 락을 넣지 않고 `@Version` + 전이 검사만 유지
- 그렇게 판단한 이유:
  - 단계 이름에 기다리는 쪽을 담으면 상태 하나가 차례를 답하므로 별도 컬럼이 필요 없음
  - 두 주체가 같은 거래를 동시에 옮길 경로가 사라져 경합 자체가 없어짐
  - 남는 경합은 같은 사람의 중복 클릭이고, 순차 도착은 전이 검사가, 완전 동시는 버전 충돌이 막음
- 고려했지만 선택하지 않은 대안:
  - 병행 체크리스트(양쪽이 각자 항목 채우고 마지막 항목에서 자동 전이)
    - 정상 흐름이 곧 동시 쓰기가 되고, JPA가 전체 컬럼을 UPDATE 하므로 상대 입력이 덮인다
    - 막으려면 진행 요청마다 `SELECT … FOR UPDATE`가 필요 — 경합을 설계로 만들고 잠금으로 수습하는 모양
  - 상태 없이 두 칸을 채우는 평면 구조 — 진행 상태·취소·귀책을 붙일 자리가 없음
  - 기존 8단계 유지 — 우리가 받아 둔 돈이 없으면 성립하지 않는 단계가 절반
- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  - 잠금 조회 메서드를 아예 두지 않아 진행 경로가 단순해짐
  - 차례 판정이 한 곳(`waitingFor()`)으로 모여 화면이 자체 표를 들지 않게 됨
  - 테스트가 "전이표를 되돌리면 깨지는" 형태로 정리됨 — 단계별 차례를 파라미터로 검증
  - 되돌릴 조건도 명시 — 기한 스케줄러가 붙거나 한 단계에 두 사람이 움직이면 비관적 락으로 재검토

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - 낙관적 락 충돌이 사용자에게 500 `INTERNAL_ERROR`로 나가고 있었음
- 처음 추측한 원인:
  - 서비스 메서드에서 예외를 잡아 도메인 에러로 바꾸면 된다고 봄
- 원인을 확인하기 위해 시도한 방법:
  - `GlobalExceptionHandler`에 등록된 핸들러 목록 확인 — `BusinessException`과 `Exception`만 있었음
  - 예외가 던져지는 시점 확인 — 버전 검사는 flush·커밋 시점이라 `@Transactional` 프록시가 커밋할 때 발생
- 실제 원인:
  - 매핑 부재로 최후 방어선(`@ExceptionHandler(Exception.class)`)에 떨어져 서버 버그로 취급됨
  - 커밋 시점 예외라 서비스 안 try-catch로는 애초에 잡히지 않음
  - 늦게 발견된 이유는 동시성 테스트가 리포지토리 계층에서 예외 타입만 확인하고 HTTP 응답을 보지 않았기 때문
- 해결 방법:
  - 공통 핸들러에 `ObjectOptimisticLockingFailureException` → 409 `CONCURRENT_MODIFICATION` 매핑 추가
  - 응답 변환을 확인하는 케이스를 기존 예외 핸들러 테스트에 추가 (경합은 동시성 테스트, 변환은 이 테스트가 담당)
- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - 새 예외 타입이 흐름에 들어오면 그것이 나가는 **HTTP 응답까지** 보는 테스트가 있는지
  - 예외가 메서드 안에서 터지는지 커밋 시점에 터지는지 (잡을 위치가 갈림)
  - 500으로 나가는 것 중 사용자가 다시 시도하면 해소되는 실패가 섞여 있지 않은지

### 4. 오늘 잘한 행동(개발과 관련된 것)

- 어떤 행동이었는지:
  - 코드보다 먼저 선택지와 기각 사유를 정리하고 이슈 본문 `## 근거`에 남긴 뒤 구현
  - 설계를 두 번 뒤집었는데(병행 → 순차, 비관적 락 도입 → 철회) 그때마다 이슈 본문을 실제 결론으로 다시 씀
  - 리뷰에서 "상세 응답에 새 값이 없다"는 지적을 받고 조회 쿼리·Row·응답 DTO까지 한 번에 확장
- 그 접근이 도움이 된 이유:
  - 결정이 바뀔 때 무엇이 전제였는지 남아 있어서, 락을 뺄 때 근거를 새로 만들지 않아도 됐음
  - 이슈 본문이 최신이라 PR 리뷰 포인트를 그대로 뽑아 쓸 수 있었음
- 다음에도 반복하고 싶은 점:
  - 결정을 되돌릴 때 기존 기록을 지우지 않고 "왜 뒤집었는지"를 같이 남기는 것
  - 검증을 "이 결정을 되돌리면 깨지는 테스트" 형태로 잡는 것

### 5. 오늘 아쉬웠던 행동(개발과 관련된 것)

- 비효율적이었던 접근/놓치거나 부족했던 점:
  - 커맨드(전이 API)만 만들고 조회 응답을 같이 늘리지 않음
    - "204를 주고 화면이 상세를 다시 읽는다"고 설계했는데, 다시 읽어도 서류·일정·금액을 알 수 없는 상태였음
    - 리뷰에서 지적받고 나서야 리드 모델을 확장
  - 상위 결정을 못 박지 않은 채 단계부터 그려서 두 번 갈아엎음
    - 보증금 유지 → 제거, 비관적 락 도입 → 철회
    - 실제로 먼저 정해야 했던 것은 "서비스가 대금을 보관하지 않는다" 한 줄
- 그렇게 된 원인:
  - 상태와 API를 쓰기의 관점으로만 봤고, 그 상태를 화면이 어떻게 읽을지를 같은 작업으로 세지 않음
  - 단계 개수·이름 같은 눈에 보이는 것부터 손댔고, 그 배경이 되는 제약(무엇을 책임지지 않을지)을 뒤늦게 확정
- 다음에는 다르게 해볼 구체적인 행동:
  - 엔티티에 필드를 추가할 때 조회 응답에 그 값이 필요한지 같은 커밋에서 판단하고, 필요 없으면 왜 없는지 적기
  - 상태 머신을 설계할 때 "이 서비스가 책임지지 않는 것"을 먼저 한 줄로 확정한 뒤 단계를 그리기
  - 전이 API를 추가하면 그 단계 화면이 필요한 값의 목록을 먼저 적어 두고 응답과 대조하기
