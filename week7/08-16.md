## be-DailyJob — 이슈 #405·#407·#411·#416 / PR #419

### 1. 오늘 완료한 것

- 오늘 실제로 끝낸 기능/수정/학습:
  - AI와 함께 k6 부하 테스트 시나리오를 작성하고, 입찰이 한 경매에 집중되는 상황을 반복해서 재현했다.
  - 테스트용 계정과 경매 데이터를 자동으로 준비하고, 워밍업 이후 가상 사용자 수를 단계적으로 높이는 실행 절차를 만들었다.
  - k6 결과와 Actuator의 Tomcat·HikariCP 지표를 함께 수집해 요청 지연이 발생하는 위치를 분석했다.
  - 입찰 요청 시간의 대부분이 실제 비즈니스 로직이 아니라 DB 커넥션 획득 대기에서 발생한다는 것을 확인했다.
  - 알림 적재 전체를 제거하는 조건과 `countUnread()`만 제거하는 조건을 각각 만들어 동일한 부하로 비교했다.
  - 느린 SSE 수신자 한 명이 `SseEmitter.send()`에서 최대 60초 동안 업무 스레드와 DB 커넥션을 점유하는 문제를 재현했다.
  - `NotificationDeliveryExecutor`를 구현해 트랜잭션 커밋 이후의 SSE 전송만 별도 실행기에서 처리하도록 변경했다.
  - 같은 회원의 알림은 FIFO로 전달하고, 서로 다른 회원의 알림은 병렬로 처리되도록 회원별 큐를 구성했다.
  - 실행기 포화 시 핵심 업무 스레드가 SSE 작업을 대신 실행하지 않도록 거절 정책을 적용했다.
  - 실행기 활성 스레드, 큐 크기, 제출·완료·거절 횟수와 SSE 전송 성공·실패·소요 시간을 측정하는 지표를 추가했다.
  - 같은 회원의 전송 순서, 다른 회원 간 격리, 큐 포화, 트랜잭션 커밋·롤백, 알림 중복 여부를 테스트로 검증했다.
- 아직 끝내지 못한 부분:
  - Tomcat 작업 스레드 200개와 HikariCP 커넥션 10개의 적정 비율은 결정하지 못했다.
  - 개발 환경에서 확인한 개선 방향을 실제 배포 환경에서도 검증하는 작업이 남아 있다.
  - 느린 SSE 연결이 4개 이상 발생하거나 다수 회원에게 알림을 팬아웃하는 상황은 추가 측정이 필요하다.
  - 서버 인스턴스가 여러 대가 되면 인스턴스 내부의 회원별 FIFO만으로 전체 순서를 보장할 수 없다는 한계가 남아 있다.

### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - 알림 저장까지 비동기로 바꾸지 않고, 기존 트랜잭션 안에서는 DB 저장과 안 읽은 알림 수 계산을 유지했다.
  - 트랜잭션 커밋 이후 실행되는 실제 SSE 소켓 전송만 전용 실행기로 분리했다.
- 그렇게 판단한 이유:
  - 알림 저장을 비동기로 옮기면 입찰이나 거래 상태 변경은 성공했지만 알림 저장은 실패하는 데이터 불일치가 발생할 수 있다.
  - 기존에는 `@TransactionalEventListener(AFTER_COMMIT)`을 사용했지만, `AFTER_COMMIT`은 실행 시점만 커밋 이후일 뿐 실행 스레드를 바꾸지 않는다.
  - 따라서 커밋을 수행한 요청 스레드가 그대로 `SseEmitter.send()`를 호출했고, 느린 수신자의 소켓 쓰기가 끝날 때까지 요청 스레드와 커넥션 반환이 지연됐다.
  - 실제 측정에서도 SSE 전송 최대 시간이 60.00초, HikariCP 커넥션 보유 최대 시간이 60.01초로 거의 일치했다.
- 고려했지만 선택하지 않은 대안:
  - `@Async`를 적용하는 방법도 검토했지만 단순 공유 스레드 풀에서는 같은 회원의 알림이 서로 다른 스레드에서 역순으로 완료될 수 있어 선택하지 않았다.
  - 특히 `unreadCount`는 증감 값이 아니라 `2`, `3`과 같은 절대값이므로 `3`이 먼저 도착하고 `2`가 나중에 도착하면 화면의 배지가 이전 값으로 되돌아갈 수 있다.
  - 전체 알림을 단일 스레드에서 처리하는 방법은 느린 사용자 한 명이 다른 모든 사용자의 알림을 막을 수 있어 제외했다.
  - 큐가 가득 찼을 때 `CallerRunsPolicy`로 업무 스레드가 전송을 대신 수행하는 방법은 기존의 지연 전파 문제를 다시 만들기 때문에 제외했다.
  - Java 21 가상 스레드 적용도 검토했지만, 이번 작업에서는 문제의 경계와 자원 상한을 명확히 검증하기 위해 고정 플랫폼 스레드를 사용했다.
- 코드 품질/테스트/유지보수에 미친 영향:
  - 업무 트랜잭션과 알림 저장의 원자성은 유지하면서 외부 소켓 I/O만 핵심 요청 경로에서 격리했다.
  - 회원별 FIFO와 전체·회원별 큐 상한이 코드에 명시되어 전달 순서와 자원 사용 정책을 테스트할 수 있게 됐다.
  - 실행기의 큐 적체와 거절 횟수를 지표로 확인할 수 있어 운영 환경에서 초기 설정값을 다시 조정할 근거가 생겼다.
  - 다만 실행기 구현에 세마포어, 회원별 큐, 실행 상태 플래그가 함께 들어가 동시성 코드의 복잡도가 증가했다.

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - 입찰 부하 테스트에서 응답 시간이 크게 증가했지만, 알림 저장·DB 행 잠금·커넥션 풀·Tomcat 스레드 중 무엇이 주된 원인인지 한 번에 구분하기 어려웠다.
  - 느린 SSE 수신자가 포함되면 입찰 p95와 p99가 약 3초까지 증가하고 `BID_LOCK_TIMEOUT`과 k6의 `dropped_iterations`가 대량으로 발생했다.
- 처음 추측한 원인:
  - 입찰 트랜잭션 안에서 이전 최고 입찰자에게 알림을 저장하고 `countUnread()`를 실행하는 과정이 경매 행 잠금 시간을 크게 늘린다고 추측했다.
  - 한 경매에 입찰이 몰리면서 `findByIdForUpdate`의 비관적 잠금 경합이 전체 지연의 대부분이라고 예상했다.
- 원인을 확인하기 위해 시도한 방법:
  - AI를 활용해 k6 시나리오와 측정 스크립트를 구성하고, 동일한 계정·시드·VU 변화·워밍업 조건을 고정했다.
  - 변경 전 기준, 알림 적재 전체 제거, `countUnread()`만 제거의 세 조건을 독립된 커밋으로 만들었다.
  - 실험 조건이 누적되지 않도록 각 변경을 `revert`하고, 동일한 기준 코드에서 다시 분기해 측정했다.
  - 입찰 한 건당 행 잠금 대기 횟수·시간, 커넥션 획득 대기·보유 시간, HikariCP pending·active, Tomcat busy, 알림 생성 수를 함께 비교했다.
  - 이후 정상 SSE만 연결한 조건과 응답을 읽지 않는 느린 SSE를 포함한 조건을 분리해 다시 측정했다.
- 실제 원인:
  - 알림 경로는 잠금을 새로 만드는 원인이 아니라 이미 획득한 경매 행 잠금의 보유 시간을 늘리는 기여자였다.
  - 알림 전체 제거 시 입찰 한 건당 잠금 대기는 22.24ms에서 14.80ms로 약 33.5% 감소했다.
  - `countUnread()`만 제거했을 때는 18.41ms로 약 17.2% 감소해 COUNT 쿼리도 유의미한 비용을 차지한다는 것을 확인했다.
  - 하지만 잠금 대기 횟수는 세 조건 모두 입찰 한 건당 1회였고, HikariCP pending 최대 189·active 최대 10·Tomcat busy 최대 200도 변하지 않았다.
  - 기준 조건에서 커넥션 획득 대기는 평균 198.1ms로 응답 중앙값의 약 82%였고, 실제 행 잠금 대기는 응답 시간의 약 9%였다.
  - 더 심각한 원인은 커밋 이후 같은 요청 스레드에서 실행되는 동기 SSE 전송이었다.
  - 느린 수신자가 있으면 `SseEmitter.send()`가 최대 60초 동안 반환되지 않았고, 그동안 업무 스레드와 DB 커넥션 반환까지 함께 지연됐다.
- 해결 방법:
  - `NotificationPusher`는 `AFTER_COMMIT` 이벤트를 받은 뒤 직접 SSE를 전송하지 않고 `NotificationDeliveryExecutor`에 작업을 제출한 후 즉시 반환하도록 변경했다.
  - 실행기는 사용자 ID별 `UserQueue`를 두어 같은 회원에게 보내는 작업을 순차적으로 실행했다.
  - 서로 다른 회원의 큐는 고정 스레드 4개에서 병렬로 처리해 느린 사용자 한 명의 영향 범위를 해당 회원으로 제한했다.
  - 전체 큐는 1,024건, 회원별 큐는 256건으로 제한해 한 사용자가 전체 큐를 독점하지 못하게 했다.
  - 큐가 가득 차면 새 SSE 전송 작업만 거절하고, 이미 커밋된 DB 알림은 유지하도록 했다.
  - 정상 SSE 2개 조건에서 서버 성공 건수와 클라이언트 수신 건수가 일치하고 중복과 순서 역전이 없는지 검증했다.
  - 느린 SSE 조건에서 변경 후 입찰 p95가 3초에서 19.12ms, p99가 3초에서 86.61ms로 감소했다.
  - `BID_LOCK_TIMEOUT`은 1,881건에서 0건, `dropped_iterations`는 4,022건에서 0건으로 줄었다.
  - HikariCP 커넥션 최대 보유 시간은 60.01초에서 134ms, Tomcat busy 최대값은 101에서 15로 감소했다.
- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - `AFTER_COMMIT`이나 이벤트 기반 코드라는 이유만으로 비동기라고 판단하지 않고 실제 실행 스레드를 확인한다.
  - 응답 시간이 느릴 때 비즈니스 로직 실행 시간뿐 아니라 커넥션 획득 대기와 반환 시점을 함께 측정한다.
  - 외부 I/O가 트랜잭션 커밋 이후에 실행되더라도 요청 스레드와 커넥션을 계속 점유하는지 확인한다.
  - 성능 가설을 검증할 때는 한 번에 하나의 코드만 제거하고, 실험 조건이 서로 누적되지 않도록 기준 커밋을 고정한다.
  - k6가 서버와 같은 장비에서 실행될 경우 부하 발생기 자체가 먼저 포화되지 않았는지도 확인한다.

### 4. 오늘 잘한 행동

- 어떤 행동이었는지:
  - AI에게 단순히 성능 개선 코드를 생성하게 하지 않고, 가설 목록과 k6 시나리오, 측정 지표, 실험 조건을 함께 검토하게 했다.
  - AI가 제안한 원인도 바로 채택하지 않고 코드 일부를 제거한 실험 빌드와 실제 수치로 검증했다.
  - 실험용 변경은 운영 코드에 설정 스위치로 남기지 않고 별도 브랜치와 커밋으로 관리한 후 원복했다.
  - 정상 사용자와 느린 사용자를 분리해 장애가 특정 연결에서 다른 요청으로 전파되는지를 직접 재현했다.
  - 비동기 처리 이후 처리량뿐 아니라 알림 저장 수, SSE 수신 수, 중복, 순서 역전과 롤백까지 확인했다.
- 그 접근이 도움이 된 이유:
  - 처음 의심한 알림 DB 작업이 실제 기여자라는 점과 주된 병목은 아니라는 점을 구분할 수 있었다.
  - 커넥션 풀 병목과 느린 SSE 전송 문제를 서로 다른 원인으로 분리해 잘못된 최적화를 피했다.
  - k6 테스트를 같은 조건으로 반복할 수 있어 감각적인 “빨라진 것 같다”가 아니라 전후 수치로 개선을 설명할 수 있었다.
  - 비동기화 과정에서 발생할 수 있는 알림 유실과 순서 역전 문제를 성능 개선과 함께 검증할 수 있었다.
- 다음에도 반복하고 싶은 점:
  - AI는 가설과 테스트 케이스를 넓히는 도구로 활용하되 최종 판단은 재현 가능한 측정 결과로 내린다.
  - 부하 테스트에서는 워밍업, 계정, 데이터, 요청률과 실행 시간을 고정해 조건 간 비교 가능성을 유지한다.
  - 처리 속도를 개선할 때는 성공률과 데이터 정합성이 그대로 유지되는지도 반드시 함께 검증한다.
  - 실험용 고장난 빌드는 PR로 올리지 않고, 커밋 SHA와 변경 내용을 결과 문서에 남겨 재현 가능성만 확보한다.

### 5. 오늘 아쉬웠던 행동

- 비효율적이었던 접근/놓치거나 부족했던 점:
  - 처음에는 알림 저장과 `countUnread()`가 주된 병목일 가능성에 집중해 커넥션 획득 대기의 비중을 늦게 확인했다.
  - k6와 WAS를 같은 로컬 장비에서 실행해 실제 배포 환경의 절대 응답 시간을 검증하지 못했다.
  - 스레드 4개와 전체 큐 1,024건, 회원별 큐 256건은 운영 측정값이 아니라 초기 안전 경계로 정했다.
  - 느린 연결이 한 개일 때만 집중적으로 측정해 실행기 스레드가 모두 느린 연결에 점유되는 상황은 확인하지 못했다.
  - 회원별 큐가 서버 메모리에 존재하므로 다중 인스턴스 환경에서는 같은 사용자의 순서를 전역적으로 보장하지 못한다.
- 그렇게 된 원인:
  - 입찰 트랜잭션 내부 코드만 먼저 보면서 요청 스레드가 커밋 이후에도 수행하는 작업을 처음부터 전체 범위로 추적하지 못했다.
  - 일정상 별도의 배포 환경과 부하 발생 서버를 준비하지 못해 로컬 전후 비교를 우선했다.
  - 현재 서비스가 단일 인스턴스라는 조건에 맞춰 서버 내부 실행기로 문제를 닫는 방향을 선택했다.
