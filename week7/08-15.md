## be-DailyJob — PR #401·#404 / 이슈 #403

### 1. 오늘 완료한 것

- 오늘 실제로 끝낸 기능/수정/학습:
  - 알림에 모델명만 표시되던 문제를 수정하고, `VehicleName` 값 객체를 도입해 `현대 코나 SX2`처럼 제조사와 모델명이 함께 표시되도록 통일했다.
  - `Manufacturer` enum이 제조사 한글 표기를 직접 가지도록 변경해 표시 이름을 만들 때 별도의 변환 로직이 필요하지 않게 했다.
  - `BidPreCheck`, `AuctionEndNotificationContext`, `AuctionStartAlertTarget`이 원시 모델명 대신 `VehicleName`을 가지도록 변경했다.
  - 평가 승인·반려 알림에는 차량 이름과 번호판을 포함하고, 거래 취소 알림에는 판매자와 딜러 중 누가 취소했는지 표시했다.
  - `application-load.yml`을 추가하고 Actuator의 `health`, `metrics` 엔드포인트와 Tomcat MBean 지표를 측정 환경에서만 노출했다.
  - `AuctionProgressScheduler`의 한 틱 실행 시간을 `System.nanoTime()`으로 측정하고, 500ms를 초과한 경우에만 경고 로그를 남겼다.
  - 알림 문구 조립과 거래 취소 주체에 따른 문구 변경을 단위 테스트와 통합 테스트로 검증했다.
- 아직 끝내지 못한 부분:
  - 로그인 검증 과정에서 발생하는 Redis 명령 호출 횟수와 왕복 지연은 아직 측정하지 못했다.
  - 부하 시나리오를 실제로 실행해 응답 시간과 Tomcat·HikariCP 지표를 비교하는 작업은 남아 있다.
  - 이번 작업에서는 커넥션 풀, 작업 스레드, 입찰 로직 등의 성능 설정을 변경하지 않았다.

### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - 성능 설정을 먼저 변경하지 않고, 측정 전용 프로파일과 지연 로그를 만들어 현재 상태를 관측하는 작업부터 진행했다.
- 그렇게 판단한 이유:
  - 서버가 느리다는 현상만으로는 Tomcat 작업 스레드 부족, HikariCP 커넥션 대기, Redis 왕복, 경매 스케줄러 지연을 구분할 수 없었다.
  - 측정과 개선을 한 PR에 함께 넣으면 변경 전후 기준이 섞여 어떤 수정이 효과를 냈는지 판단하기 어렵다.
- 고려했지만 선택하지 않은 대안:
  - Tomcat 스레드와 HikariCP 커넥션 풀을 바로 늘리는 방법은 병목 근거가 없어서 선택하지 않았다.
  - 모든 경매 스케줄러 틱을 로그로 남기는 방법은 500ms 주기마다 로그 I/O가 발생해 측정 결과를 왜곡할 수 있어 제외했다.
  - Actuator 지표를 기본 프로파일에서 열고 운영 환경에서만 닫는 방법은 설정 누락 시 무인증 지표가 노출될 수 있어 제외했다.
- 코드 품질/테스트/유지보수에 미친 영향:
  - `load` 프로파일을 사용할 때만 관측 기능이 활성화되므로 일반 실행과 운영 환경의 노출 범위가 변하지 않았다.
  - 실제 성능 개선 PR에서 측정 전후 결과를 동일한 기준으로 비교할 수 있는 기반이 생겼다.
  - 스케줄러가 기준 시간을 넘긴 사건만 기록해 로그 양을 제한하면서 실제 지연 시간은 사후 분석할 수 있게 했다.

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - 알림마다 차량을 표시하는 방식이 달라 어떤 알림에는 모델명만 나오고, 평가 알림에서는 같은 차종의 차량을 구분하기 어려웠다.
  - 차량 이름을 값 객체로 바꾸자 JPQL 생성자 표현식과 경매가 존재하지 않을 수 있는 좌측 조인 결과를 함께 처리해야 했다.
- 처음 추측한 원인:
  - 알림 문자열 템플릿에 제조사만 추가하면 해결할 수 있다고 생각했다.
- 원인을 확인하기 위해 시도한 방법:
  - 입찰, 경매 시작·종료, 평가, 방문견적, 거래 진행에서 알림에 전달되는 차량 데이터를 추적했다.
  - Repository의 JPQL `select new` 결과가 어떤 생성자를 호출하는지와 좌측 조인 시 차량 필드가 `null`이 되는 경우를 확인했다.
- 실제 원인:
  - 알림 계층에는 제조사 정보가 전달되지 않았고, 각 기능이 모델명 문자열을 개별적으로 사용하고 있었다.
  - 단순히 문자열을 추가하면 동일한 조합 규칙이 여러 서비스에 중복되고, JPQL 조회 결과와 도메인 표현도 계속 달라지는 구조였다.
- 해결 방법:
  - 제조사와 모델명을 묶는 `VehicleName`을 만들고 생성자에서 제조사가 없는 잘못된 상태를 차단했다.
  - 관련 Repository의 조회 항목에 제조사를 추가하고, JPQL 생성자 표현식에서 사용할 생성자를 별도로 제공했다.
  - 경매가 없을 수 있는 `BidPreCheck`에서는 좌측 조인 결과가 비어 있을 때 `VehicleName`을 생성하지 않도록 처리했다.
  - `NotificationContent`가 알림 종류별 문구를 발행 시점에 조립하도록 하고, `DealSide`가 취소 주체의 사용자용 표기를 책임지게 했다.
  - 단계별 알림 문구와 판매자·딜러 취소에 따른 문구 반전을 테스트로 고정했다.
- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - 화면 문구만 수정하기 전에 표시 정보가 어느 조회에서 만들어지고 어떤 도메인 객체를 거쳐 전달되는지 전체 경로부터 확인한다.
  - JPQL 생성자 표현식에 값 객체를 도입할 때는 생성자 시그니처와 외부 조인의 `null` 가능성을 먼저 검사한다.

### 4. 오늘 잘한 행동

- 어떤 행동이었는지:
  - 알림 문자열을 각 서비스에서 직접 이어 붙이지 않고 `VehicleName`, `NotificationContent`, `DealSide`로 책임을 나눴다.
  - 성능 문제도 추측으로 수정하지 않고 이슈 #403에 측정 대상, 선택지, 기각 이유와 판단을 뒤집을 조건까지 정리했다.
- 그 접근이 도움이 된 이유:
  - 차량 표시 규칙이 한 곳에 모여 새로운 알림을 추가해도 동일한 이름을 재사용할 수 있게 됐다.
  - 알림 문구 생성과 거래 상태 변경 로직이 분리돼 서비스 코드가 사용자 문구 세부사항을 덜 알게 됐다.
  - 성능 개선 전에 Tomcat 스레드, HikariCP 커넥션, JVM 상태, 스케줄러 지연을 서로 구분해 볼 수 있게 됐다.
- 다음에도 반복하고 싶은 점:
  - 여러 도메인에서 반복되는 표현 규칙은 원시 문자열 대신 값 객체로 모델링한다.
  - 성능 문제는 가설, 측정 지표, 합격선, 변경 전 수치를 먼저 남긴 뒤 코드를 수정한다.
  - 문구처럼 사소해 보이는 변경도 분기별 결과가 다르면 단위 테스트와 통합 테스트로 함께 검증한다.

### 5. 오늘 아쉬웠던 행동

- 비효율적이었던 접근/놓치거나 부족했던 점:
  - 차량 표시 이름 변경이 입찰, 경매, 평가, 거래와 JPQL 조회까지 연결돼 있었는데 초기에 영향 범위를 작게 예상했다.
  - 관측 환경을 구축했지만 같은 날 실제 부하 테스트를 실행해 베이스라인을 남기지는 못했다.
- 그렇게 된 원인:
  - 알림 문구를 프레젠테이션 계층의 문자열 변경으로 생각했지만, 실제로는 조회 데이터와 도메인 표현을 함께 변경해야 하는 작업이었다.
  - 측정 환경 구축과 실제 실험을 하나의 작업 단위로 계획해 시간 배분이 명확하지 않았다.
- 다음에는 다르게 해볼 구체적인 행동:
  - 공통 값 객체를 도입하기 전에 해당 원시 값을 사용하는 Repository, DTO, 서비스, 테스트를 먼저 검색해 변경 범위를 산정한다.
  - JPQL 프로젝션 변경 시 생성자 시그니처, `null` 가능성, 쿼리 실행 테스트를 체크리스트로 확인한다.
  - 관측 환경 구축과 부하 실험을 별도 작업으로 나누고, 환경 구축 직후 작은 부하라도 실행해 최초 베이스라인을 남긴다.
  - 다음 작업에서는 Redis 지표로 로그인 요청당 명령 횟수와 왕복 지연을 확인한 뒤, 필요할 때만 애플리케이션 계측을 추가한다.
