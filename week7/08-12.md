### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - 경매 시작 알림 신청 행을 발송 이력으로 계속 보관하지 않고, **아직 처리하지 않은 신청 목록**으로 사용
  - 경매 시작 상태 전이와 알림 팬아웃을 같은 잠금 구간에서 처리하지 않고, 시작·종료 전이가 끝난 뒤 스케줄러 마지막 단계에서 발송
  - 알림 저장과 신청 삭제는 한 트랜잭션으로 묶어 성공한 신청만 제거
- 그렇게 판단한 이유:
  - 행이 존재하면 아직 보내지 않은 신청이고, 행이 없으면 처리 완료라는 의미가 되어 별도 `sent` 컬럼이 필요 없음
  - 알림 저장 중 실패하면 트랜잭션이 롤백되어 신청 행이 남으므로 다음 주기에 다시 처리할 수 있음
  - 성공하면 알림과 삭제가 함께 커밋되어 같은 신청이 다시 후보로 잡히지 않음
  - 경매 시작 로직은 경매 행을 `SELECT … FOR UPDATE`로 잠그므로 그 안에서 신청자 수만큼 알림을 저장하면 시작 직후 입찰이 기다리게 됨
  - 경매 진행 스케줄러는 단일 스레드라 팬아웃을 앞에 두면 시작과 낙찰 확정까지 함께 밀림
- 고려했지만 선택하지 않은 대안:
  - 경매 시작 전이 내부에서 신청자 알림을 모두 저장
    - 시작과 알림의 원자성은 강하지만 경매 잠금 시간이 신청자 수에 비례해 늘어남
  - `Notification`을 예약 상태로 미리 생성
    - 아직 발송하지 않은 알림이 목록과 안 읽은 건수에 섞이고 모든 조회에 예약 상태 제외 조건이 필요함
  - 신청 행에 `sent` 컬럼을 추가
    - 이력은 남지만 발송 여부와 재시도 상태를 함께 관리해야 하고 현재 요구에는 과함
  - 알림 발송을 즉시 비동기로 분리
    - 순서·실패·재시도·백프레셔를 새로 설계해야 하는데 아직 팬아웃 병목이 측정되지 않음
- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  - 발송 여부 컬럼 없이 신청 테이블 자체가 처리 대기 목록 역할을 하게 됨
  - 경매 시작과 낙찰 확정이 알림 팬아웃보다 우선된다는 순서가 스케줄러 코드에 드러남
  - 실패한 신청은 별도 복구 코드 없이 다음 주기에 자동으로 다시 처리됨
  - 한 주기의 상한을 경매 수가 아니라 신청 행 100건으로 계산해 팬아웃 크기에 상한을 둠
  - 서버 중단으로 시작과 종료가 같은 주기에 처리된 경매는 뒤늦은 시작 알림을 보내지 않고 신청만 정리

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - 구현 자체보다 신청 저장·중복 요청·경매 시작과의 경합·발송 실패·팬아웃 위치를 어떤 기준으로 나눌지 결정하는 데 예상보다 많은 시간이 들었음
  - 각각만 보면 단순한 선택이었지만 함께 연결하면 한 결정을 바꿀 때 다른 결정의 근거도 같이 바뀌었음
- 처음 생각한 방향:
  - 신청은 `auction` 도메인이 소유
  - 중복은 `exists` 조회와 유일 제약으로 방지
  - 신청 API는 `POST`
  - `AuctionStarter`가 시작 전이 직후 같은 트랜잭션에서 신청자 알림까지 저장
  - 신청 여부는 대기방 응답에 포함
- 검토하면서 발견한 문제:
  - 중복 신청만 막는 유일 제약으로는 `시작 전 확인 → 신청 저장` 사이에 경매가 시작되는 시간 경합을 막을 수 없었음
  - 시작 전이 안에서 팬아웃하면 경매 행을 잠근 채 신청자 수만큼 알림 INSERT와 안 읽은 건수 COUNT를 수행하게 됨
  - 대기방 응답에 신청 여부를 넣으면 의도적으로 비개인화돼 있던 응답의 전제가 깨지고, 경매 미리보기 화면에서는 다시 별도 계약이 필요함
  - 신청자 수를 경매 단위로 제한하면 신청자가 많은 경매 하나가 한 주기의 처리 시간을 전부 사용할 수 있음
  - `IN_PROGRESS`만 발송 대상으로 보면 서버 중단 중 시작과 종료가 모두 지난 경매의 신청 행이 영구히 남음
- 판단 기준으로 먼저 확정한 것:
  - 경매가 실제로 시작되기 전에는 알림을 보내지 않음
  - 시작된 뒤에는 새로운 신청을 받지 않음
  - 알림 발송 실패가 시작·낙찰 상태 전이를 막지 않음
  - 실패한 신청은 다음 주기에 다시 처리할 수 있어야 함
  - 시작 알림을 늦게 보내는 것은 허용하지만 경매 시작과 낙찰 확정을 늦추지는 않음
  - 미리보기와 대기방은 서로 다른 응답 구조여도 같은 서버 저장값을 봐야 함
- 해결 방법:
  - 신청 시 경매 행을 짧게 잠그고, 잠금을 얻은 뒤 서버 시각으로 신청 가능 여부를 다시 판정
    - 신청이 먼저면 저장 후 경매 시작
    - 경매 시작이 먼저면 신청 거절
  - 같은 회원의 동시 신청도 경매 잠금으로 순서가 정해져 두 번째 요청이 `exists`에서 종료되도록 구성
  - API는 요청 주소가 `이 경매에 대한 내 시작 알림 신청`이라는 단일 자원을 나타내므로 `PUT`으로 변경
    - 최초 신청은 201, 이미 신청한 상태면 204
  - 신청 여부는 대기방 응답에 섞지 않고 `GET /api/auctions/{id}/start-alert`로 분리
    - 미리보기와 대기방이 동일한 계약을 공유
  - 발송은 `AuctionStarter`에서 분리해 경매 진행 스케줄러의 시작·종료 처리 이후에 배치
  - 알림 저장과 신청 삭제를 한 트랜잭션으로 묶고, 신청 식별자를 사용해 한 번에 벌크 삭제
  - 처리 후보는 `IN_PROGRESS`, `ENDED`, `FAILED`만 조회
    - 예정 경매가 처리 상한을 차지하지 않게 함
    - 이미 종료된 경매는 시작 알림 없이 신청만 정리
  - 한 주기의 처리 상한은 경매 수가 아니라 신청 행 100건으로 설정
- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - 기능 목록보다 먼저 지켜야 하는 불변식과 실패했을 때 남아야 하는 데이터를 작성
  - 중복 요청 경합과 상태가 바뀌는 시간 경합을 서로 다른 문제로 구분
  - 잠금 안에 추가되는 쿼리 수가 동시 요청 대기 시간에 어떻게 곱해지는지 확인
  - 스케줄러 작업은 실패 복구뿐 아니라 앞뒤 작업의 우선순위까지 먼저 결정
  - 발송 상한을 부모 사건 수로 셀지 실제 작업 행 수로 셀지 확인

### 4. 오늘 잘한 행동(개발과 관련된 것)

- 어떤 행동이었는지:

    - `POST`에서 `PUT`으로 변경
    - `AuctionStarter` 내부 발송에서 스케줄러 후행 단계로 변경
    - 대기방 응답 필드에서 별도 신청 조회 API로 변경
  - 구현 후 신청자 수와 대상 경매 수를 로그로 남겨 향후 팬아웃 분리 여부를 판단할 측정 지점을 확보
  - 단순 성공 경로뿐 아니라 동시 신청·정각 경계·서버 중단 후 종료 경매 정리·처리 상한 분할을 테스트
- 그 접근이 도움이 된 이유:
  - 착수 단계에서 세운 가정과 실제 코드 구조가 어긋나는 지점을 구현 전에 발견할 수 있었음
  - 왜 경매 행을 잠그면서도 알림 발송은 잠금 밖으로 뺐는지 서로 모순 없이 설명할 수 있게 됨
  - 실패한 신청이 유실되지 않고 다음 주기에 다시 처리된다는 성질을 별도 재시도 테이블 없이 확보
  - 리뷰 포인트가 코드 설명이 아니라 판단의 대가와 재검토 조건을 묻는 형태로 정리됨
- 다음에도 반복하고 싶은 점:
  - 착수 브리핑을 정답이 아니라 검증할 가설로 사용하는 것
  - 구현하면서 전제가 달라지면 결정과 근거를 함께 수정하는 것
  - 테스트를 선택한 결정을 되돌리면 깨지는 시나리오로 작성하는 것
  - 최적화를 바로 넣지 않고 먼저 관측할 숫자와 뒤집을 조건을 남기는 것

### 5. 오늘 아쉬웠던 행동(개발과 관련된 것)

- 비효율적이었던 접근/놓치거나 부족했던 점:
  - 신청 기능을 처음 검토할 때 일곱 가지 결정을 각각 따로 판단해 전체 기준을 확정하는 데 시간이 많이 들었음
  - API 메서드·응답 위치·발송 호출부처럼 코드 모양부터 고르면서, 뒤에서 잠금과 실패 복구 조건을 발견할 때마다 앞선 결론을 다시 수정함
  - 초기에는 “시작 전이와 알림을 원자적으로 묶는다”는 장점에 집중해 팬아웃이 경매 잠금과 단일 스케줄러에 미치는 영향을 늦게 확인함
  - 코드량은 크지 않았지만 동시성·트랜잭션·스케줄러 우선순위·화면 계약을 계속 오가며 판단해 예상보다 훨씬 오래 걸림
- 그렇게 된 원인:
  - 중복 신청 방지, 시작 전 판정, 발송 재시도를 모두 멱등성 하나의 문제로 묶어서 봄
    - 실제로는 중복 행 방지, 시간 경합, 실패 복구가 서로 다른 문제였음
  - “어디에서 호출할까”를 먼저 생각했고 “무엇이 실패해도 무엇은 반드시 진행돼야 하는가”를 늦게 정함
  - 대기방 요청 횟수를 줄이는 데 집중해 비개인화 응답을 개인화하는 장기 비용을 처음에는 충분히 보지 못함
- 다음에는 다르게 해볼 구체적인 행동:
  - 구현 전에 아래 기준부터 한 줄씩 확정
    - 성공 후 반드시 함께 남아야 하는 데이터
    - 실패하면 다음 시도까지 남아야 하는 데이터
    - 잠금을 잡아야만 정확한 판정
    - 잠금 밖으로 빼야 하는 부가 작업
    - 사용자 화면들이 공유해야 하는 서버 계약
  - 동시성 문제를 `중복 요청`, `상태 변경과의 경합`, `실패 후 재처리`로 나눠 각각의 방어 수단을 선택
  - 스케줄러 기능은 `시작 → 종료 → 부가 알림`처럼 업무 우선순위를 먼저 정한 뒤 호출 위치 결정
  - 새 응답 필드를 기존 API에 얹기 전에 그 응답이 개인화돼도 되는 계약인지 확인
  - 선택지가 많을수록 코드 형태를 먼저 고르지 않고, 반드시 지킬 불변식과 허용할 지연부터 작성
