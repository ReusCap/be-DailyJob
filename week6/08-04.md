# be-DailyJob

### 1. 오늘 완료한 것

- 오늘 실제로 끝낸 기능/수정/학습:
  - 회원별 알림 목록 조회, 안 읽은 알림 수 조회, 개별 읽음 처리, 전체 읽음 처리 API를 개발하고 PR을 올렸다
  - 알림 목록을 최신순 10건씩 가져오는 커서 페이징을 구현했다
  - 알림 종류가 기본 문구와 이동할 화면 주소 규칙을 함께 갖도록 `NotificationType`을 정리했다
  - 응답에는 `referenceId` 대신 서버에서 완성한 `link`를 내려주도록 했다
  - 목록 조회에 엔티티 대신 JPQL 생성자 프로젝션인 `NotificationRow`를 사용했다
  - 읽음 처리를 벌크 UPDATE로 구현하고 `@Modifying(clearAutomatically = true)`를 적용했다
  - 인증, 소유권, 페이징, 멱등성, 링크 조립을 포함한 통합 테스트 8개 시나리오를 작성했다
  - JPQL, N+1, OSIV, 커서 페이징, 읽기 전용 트랜잭션, JPA 영속성 컨텍스트를 공부했다

- 아직 끝내지 못한 부분:
  - 낙찰, 거래 단계 전이, 평가 승인 시점에 실제 알림을 발행하는 연결 작업은 남아 있다
  - 저장된 알림을 SSE로 실시간 전달하는 작업은 별도 범위로 남겼다
  - `NotificationType`이 프론트 라우트 경로를 아는 것이 도메인 책임으로 적절한지 리뷰가 필요하다
  - 회원별 알림이 실제로 많이 쌓였을 때 추가 복합 인덱스가 필요한지는 운영 데이터로 확인해야 한다

### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - 알림 목록의 정렬 기준과 다음 페이지 커서를 모두 생성 시각이 아니라 증가하는 식별자 ID로 통일했다

- 그렇게 판단한 이유:
  - `createdAt`은 고유한 값이 아니어서 같은 시각에 여러 알림이 만들어지면 순서가 결정되지 않는다
  - 정렬 기준과 커서가 불안정하면 첫 페이지를 읽은 뒤 새 알림이 추가됐을 때 다음 페이지에서 기존 알림이 중복되거나 빠질 수 있다
  - Auto Increment ID는 단조 증가하므로 `id < :cursor order by id desc` 조건으로 이미 본 영역과 다음 영역을 명확히 나눌 수 있다
  - 전체 건수를 세지 않고 11건을 조회해 10건만 반환하는 방식으로 다음 페이지 존재 여부도 판단할 수 있다

- 고려했지만 선택하지 않은 대안:
  - 생성 시각을 커서로 쓰는 방식은 화면의 최신순 의미와 직관적으로 맞지만 같은 시각의 행을 안정적으로 구분하지 못해 기각했다
  - `createdAt`과 ID를 묶은 복합 커서도 가능하지만 현재는 ID 자체가 생성 순서를 충분히 표현해서 복잡도를 추가하지 않았다
  - 오프셋 페이징은 구현이 단순하지만 페이지 사이에 새 알림이 추가되면 행 위치가 밀려 중복이나 누락이 발생할 수 있어 선택하지 않았다
  - 페이지 크기를 클라이언트가 받도록 하면 유연하지만 상한 검증이 필요하고 현재 드롭다운과 목록 모두 10건이면 충분해 고정했다

- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  - 조회 조건이 `userId`, `id < cursor`, `id desc`로 단순해졌다
  - 페이지를 넘기는 중간에 알림이 새로 쌓여도 처음 존재했던 알림을 중복이나 누락 없이 읽을 수 있게 됐다
  - 고정된 시각으로 모든 알림의 `createdAt`을 같게 만든 통합 테스트를 통해 ID 커서 선택의 이유가 코드로 남았다
  - ID가 생성 순서를 대표한다는 현재 전제가 바뀌면 커서 정책도 함께 다시 검토해야 한다

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - 읽음 처리를 JPQL 벌크 UPDATE로 구현하면 DB의 `isRead`는 `true`인데 같은 트랜잭션의 엔티티는 계속 `false`를 반환할 수 있었다

- 처음 추측한 원인:
  - UPDATE가 실행되면 JPA가 관리 중인 엔티티에도 변경된 값이 자동으로 반영될 것이라고 생각했다

- 원인을 확인하기 위해 시도한 방법:
  - 엔티티 조회, 벌크 UPDATE, 같은 엔티티 재조회 순서로 영속성 컨텍스트와 DB의 상태가 어떻게 달라지는지 정리했다
  - `@Modifying`의 `clearAutomatically`와 `flushAutomatically`가 각각 언제 필요한지 확인했다
  - 테스트에는 `@Transactional`을 붙이지 않고 실제 요청처럼 서비스 트랜잭션이 끝난 뒤 DB를 직접 조회해 갱신 결과를 확인했다

- 실제 원인:
  - JPQL 벌크 UPDATE는 영속성 컨텍스트의 변경 감지 경로를 거치지 않고 DB에 직접 쿼리를 실행한다
  - 이미 조회한 엔티티가 1차 캐시에 있으면 DB가 변경돼도 캐시에는 이전 `isRead = false` 상태가 남는다
  - 같은 트랜잭션에서 다시 조회하면 DB가 아니라 1차 캐시의 오래된 값이 반환될 수 있다

- 해결 방법:
  - 읽음 처리 쿼리에 `@Modifying(clearAutomatically = true)`를 적용해 벌크 연산 직후 영속성 컨텍스트를 비우도록 했다
  - 개별 읽음 조건에 알림 ID와 사용자 ID를 함께 넣어 남의 알림과 없는 알림이 모두 영향 행 0건으로 나오게 했다
  - 개별 읽음은 이미 읽은 알림도 갱신 대상에 포함해 같은 요청을 두 번 보내도 성공하도록 했다
  - 전체 읽음은 `isRead = false`인 내 알림만 갱신해 이미 읽은 행까지 다시 쓰지 않도록 했다

- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - `@Query`로 UPDATE나 DELETE를 실행하면 DB와 1차 캐시가 자동으로 동기화되지 않는다고 전제한다
  - 벌크 연산 전에 아직 flush되지 않은 엔티티 변경이 있다면 `flushAutomatically = true`까지 필요한지 확인한다
  - 통합 테스트의 트랜잭션이 운영 요청과 다른 영속성 컨텍스트 수명을 만들고 있지 않은지 본다
  - 갱신된 엔티티를 같은 트랜잭션에서 다시 사용할 필요가 있는지도 먼저 확인한다

### 4. 오늘 잘한 행동

- 어떤 행동이었는지:
  - 엔티티를 그대로 반환하지 않고 필요한 필드만 조회하는 `NotificationRow` 프로젝션을 만들었다
  - 커서 선택의 근거를 설명으로만 남기지 않고 모든 생성 시각을 같게 고정한 통합 테스트로 검증했다
  - 남의 알림과 없는 알림을 같은 404로 응답하게 하고, 그 결과가 같은지 테스트했다
  - 알림을 SQL 픽스처로 바로 넣지 않고 도메인 생성 메서드로 만들어 문구와 링크 규칙까지 함께 검증했다
  - `JpaRepository` 대신 `Repository<Notification, Long>`를 사용해 실제로 필요한 메서드만 노출했다

- 그 접근이 도움이 된 이유:
  - 프로젝션으로 필요한 값만 한 번에 가져오니 지연 로딩과 OSIV에 기대는 조회 경로가 생기지 않았다
  - 페이지 사이에 새 알림 3건을 넣는 테스트가 실제로 중복과 누락이 없다는 것을 보여줘 설계 의도가 깨지기 어려워졌다
  - 소유권 확인을 UPDATE의 WHERE 조건에 넣어 조회 쿼리를 줄였고, 다른 사람의 알림 존재 여부도 노출하지 않았다
  - 삭제할 이유가 없는 기록에 `deleteAll()` 같은 메서드가 열리지 않아 저장소의 사용 범위가 도메인 의도와 맞아졌다

- 다음에도 반복하고 싶은 점:
  - 성능이나 정합성 판단은 주석만 남기지 않고 그 판단이 틀리면 실패하는 테스트로 고정한다
  - 목록 API는 엔티티 전체가 정말 필요한지 먼저 보고 DTO 프로젝션이나 Fetch Join을 선택한다
  - 권한 검사는 데이터를 가져온 다음 비교하기보다 가능하면 조회·갱신 조건 자체에 포함한다
  - 통합 테스트는 공통 `IntegrationTestSupport`를 사용하고 실제 운영 요청과 비슷한 트랜잭션 경계를 유지한다

### 5. 오늘 아쉬웠던 행동

- 비효율적이었던 접근/놓치거나 부족했던 점:
  - 알림 문구와 링크 누락을 막으려고 `NotificationType`에 프론트 라우트까지 넣었지만 표현 계층의 지식이 도메인으로 들어온 문제가 남았다
  - JPQL, OSIV, N+1, QueryDSL, 더티 체킹까지 한꺼번에 공부하면서 당장 알림 조회 구현에 직접 쓰이지 않는 범위까지 넓어졌다
  - 인덱스를 추가하지 않는 판단을 현재 예상 데이터 규모에 기대어 내렸고 실제 실행 계획이나 부하 측정으로 확인하지는 않았다
  - 새 API를 만들 때 `@LoginUser`만 붙이면 인증된다고 생각할 수 있었고 `AuthWebMvcConfig` 경로 등록을 별도로 확인해야 했다

- 그렇게 된 원인:
  - 알림 종류를 추가할 때 문구와 링크 중 하나를 빠뜨리는 문제를 막는 데 집중해 계층 간 책임까지 완전히 정리하지 못했다
  - JPA 조회와 갱신의 배경을 한 번에 이해하려다 학습 범위를 좁히지 않았다
  - 회원 한 명당 알림이 수십 건일 것이라는 가정이 있어 인덱스 효과를 측정할 우선순위를 낮게 봤다
  - 인증이 애너테이션 하나가 아니라 인터셉터의 경로 패턴과 함께 동작한다는 프로젝트 구조를 먼저 확인하지 않았다

- 다음에는 다르게 해볼 구체적인 행동:
  - 리뷰를 통해 알림 문구와 링크를 함께 강제하면서도 도메인이 화면 경로를 직접 알지 않는 구조가 가능한지 비교한다
  - 학습 전에 현재 구현에서 답해야 할 질문을 먼저 적고, 관련 없는 개념은 후속 공부 목록으로 분리한다
  - 알림 데이터가 늘어나면 `user_id`, `id`, `is_read` 조건의 실행 계획과 응답 시간을 측정한 뒤 인덱스를 추가한다
  - 인증이 필요한 API를 추가할 때 `@LoginUser`, 인터셉터 경로, 쿠키 없는 요청의 401 테스트를 하나의 체크리스트로 확인한다
  - 벌크 연산과 boolean 응답 필드는 각각 영속성 컨텍스트 초기화와 JSON 필드명이 의도대로 나가는지 통합 테스트로 확인한다
