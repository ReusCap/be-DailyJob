## be-DailyJob

### 1. 오늘 완료한 것

- 오늘 실제로 끝낸 기능/수정/학습:
  - 낙찰 이후 거래가 생성되고 완료까지 순서대로 진행되는 상태 전이 규칙을 구현했다
  - 거래 단계를 8개로 나누고 건너뛰기, 되돌아가기, 같은 요청 재처리를 막았다
  - 낙찰 확정과 거래 생성을 같은 트랜잭션으로 묶어 거래 없는 낙찰이 남지 않게 했다
  - 거래 단계가 동시에 변경될 때 한 요청만 성공하도록 낙관적 락을 적용했다
  - 판매와 구매 거래를 한 목록에서 조회하는 API와 거래 상세 조회 API를 구현했다
  - 거래 당사자가 아닌 사용자는 존재하지 않는 거래와 동일하게 404를 받도록 조회 조건에서 걸렀다
  - 식별자 커서 페이징과 DTO 조회를 적용하고 거래 수가 늘어도 쿼리 수가 증가하지 않는지 테스트했다

- 아직 끝내지 못한 부분:
  - 각 거래 단계에서 실제 행동을 처리하는 API와 화면 연동은 후속 작업으로 남았다
  - 기한 초과 취소와 정산 실패처럼 정상 전이 밖의 예외 흐름은 아직 구현하지 못했다
  - 거래 목록과 상세 응답이 실제 화면 요구사항을 모두 충족하는지는 프론트 연동 과정에서 추가로 확인해야 한다

### 2. 오늘 가장 의미있었던 기술적 판단

- 내가 내린 판단:
  - 거래 진행 규칙을 서비스의 조건문으로 흩어놓지 않고 `Deal`과 `DealStatus`가 직접 검증하도록 만들었다

- 그렇게 판단한 이유:
  - 거래는 순서를 건너뛰거나 이전 단계로 돌아가면 보증금, 서류, 탁송 상태가 서로 맞지 않게 된다
  - 상태를 단순히 다음 값으로 변경하면 같은 요청이 두 번 들어왔을 때 잘못된 단계까지 넘어갈 수 있다
  - 판매자와 구매자가 동시에 단계를 변경할 수 있어서 애플리케이션 검증만으로는 동시 요청을 막을 수 없다
  - 취소는 정상 전이와 달리 사유와 귀책 정보가 반드시 필요해서 일반 전이와 분리해야 했다

- 고려했지만 선택하지 않은 대안:
  - 서비스마다 현재 상태를 확인하는 방식은 전이 규칙이 여러 곳에 중복되고 새 단계가 추가될 때 일부 코드가 빠질 수 있어서 선택하지 않았다
  - 상태를 단순 setter로 변경하는 방식은 건너뛰기와 재요청을 엔티티가 막을 수 없어서 사용하지 않았다
  - 비관적 락은 모든 전이 요청이 DB 락을 기다려야 하고 실제 충돌 빈도가 높지 않아서 적용하지 않았다
  - 취소를 정상 전이표에 포함하는 방식은 사유 없는 취소가 가능해질 수 있어서 분리했다

- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  - 단계 추가 시 `switch`의 전이 규칙도 함께 수정해야 해서 누락이 빌드 과정에서 드러나게 됐다
  - 건너뛰기, 되돌아가기, 재요청, 동시 전이를 각각 테스트로 고정할 수 있었다
  - 거래 생성과 전이 규칙을 호출하는 쪽에서는 상태 변경 세부 조건을 다시 구현하지 않아도 됐다
  - 낙찰가와 단계 변경 시각을 거래가 따로 보관해 경매 가격 변경이나 배송지 수정이 거래 기록에 영향을 주지 않게 됐다

### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상:
  - 거래 목록을 조회할 때 어떤 값을 커서로 사용해야 조회 중 단계가 바뀌어도 중복이나 누락이 생기지 않는지 고민했다

- 처음 추측한 원인:
  - 거래를 최근 진행 순서로 보여주려면 단계 변경 시각을 정렬과 커서에 함께 사용하면 된다고 생각했다

- 원인을 확인하기 위해 시도한 방법:
  - 페이지를 읽는 사이 거래 단계가 변경되는 경우를 테스트로 만들었다
  - 여러 거래의 마감 시각을 같게 만든 뒤 다음 페이지 결과가 안정적으로 유지되는지 확인했다
  - 조회 도중 새 거래가 추가됐을 때 첫 페이지에서 읽은 거래가 다음 페이지로 밀리는지도 확인했다

- 실제 원인:
  - 단계 변경 시각은 거래가 진행될 때마다 바뀌는 값이라 커서로 사용하면 페이지 사이에서 정렬 순서가 달라진다
  - 변경 가능한 값을 커서로 잡으면 같은 거래가 다시 보이거나 아직 보지 않은 거래를 건너뛸 수 있었다

- 해결 방법:
  - 거래 생성 이후 바뀌지 않는 식별자를 커서로 사용하고 식별자 내림차순으로 조회했다
  - 요청한 크기보다 한 건 더 조회해 전체 개수를 세지 않고 다음 페이지 존재 여부를 판단했다
  - 동일한 시각의 거래와 조회 중 신규 거래 생성 상황을 통합 테스트로 고정했다

- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - 페이징 커서 후보가 조회 도중 변경될 수 있는 값인지 먼저 확인한다
  - 정상 데이터만 보지 않고 조회 사이에 추가와 수정이 발생하는 경우부터 테스트한다
  - 화면에서 원하는 정렬 기준과 안정적인 페이징 기준을 반드시 같은 값으로 써야 하는지 구분한다

### 4. 오늘 잘한 행동

- 어떤 행동이었는지:
  - 구현한 결과만 테스트하지 않고 선택한 설계가 다시 깨지는 상황을 테스트로 만들었다
  - 낙찰, 유찰, 재종료에서 거래 생성 건수를 각각 확인했다
  - 거래 생성이 실패하면 낙찰 확정과 알림도 함께 롤백되는지 확인했다
  - 목록 데이터가 늘어도 쿼리 수가 증가하지 않는지 실제 Hibernate 통계로 확인했다
  - 상대 이름을 조회한 직후 마스킹하고 원본 이름이 이후 계층에 남지 않게 했다

- 그 접근이 도움이 된 이유:
  - 상태 전이 규칙과 트랜잭션 경계가 코드 설명이 아니라 실패하는 테스트로 남았다
  - N+1 문제가 다시 생기면 목록 건수에 따라 쿼리 수가 증가하는 테스트에서 바로 확인할 수 있다
  - 남의 거래와 없는 거래를 같은 응답으로 처리해 거래 존재 여부가 노출되지 않게 했다
  - 목록과 상세 조회 모델을 나눠 목록 여러 건에서 상세 전용 데이터를 반복해서 읽지 않게 했다

- 다음에도 반복하고 싶은 점:
  - 구현 전에 바뀌면 안 되는 값을 먼저 정하고 테스트로 고정한다
  - 동시 요청과 롤백처럼 정상 흐름 밖의 상황을 통합 테스트에 포함한다
  - 조회 API는 응답 데이터뿐 아니라 쿼리 횟수와 권한 조건도 함께 검증한다

### 5. 오늘 아쉬웠던 행동

- 비효율적이었던 접근/놓치거나 부족했던 점:
  - OSIV가 켜져 있다는 잘못된 전제로 주석을 작성했다가 실제 설정을 확인한 뒤 수정했다
  - 목록 크기를 주석에 구체적인 숫자로 적어 설정값이 바뀌면 설명이 틀려지는 부분이 있었다
  - 상태 모델과 조회 API를 먼저 완성했지만 실제 단계별 행동 API까지 한 흐름으로 검증하지는 못했다

- 그렇게 된 원인:
  - 현재 설정을 직접 확인하지 않고 이전에 알고 있던 Spring 기본 동작을 기준으로 판단했다
  - 코드가 아니라 당시의 숫자를 설명하는 주석을 작성했다
  - 거래 도메인 범위가 커서 생성, 전이, 조회를 먼저 나누는 데 집중했고 전체 사용자 흐름 검증은 뒤로 밀렸다

- 다음에는 다르게 해볼 구체적인 행동:
  - JPA와 트랜잭션 동작을 설명할 때는 `application.yml`의 실제 설정부터 확인한다
  - 주석에는 쉽게 바뀌는 숫자보다 목록과 상세를 분리한 이유를 남긴다
  - 단계별 행동 API를 추가할 때 상태 전이, 권한, 동시 요청을 하나의 통합 테스트에서 함께 검증한다
  - 프론트 연동 전에 각 거래 단계에서 누가 어떤 요청을 보낼 수 있는지 API 계약을 먼저 정리한다
